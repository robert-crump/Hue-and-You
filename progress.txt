## 2026-09-25 - Issue #21: Skip white calibration and auto-pick the main color from the center box

Deleted `WhiteBalanceCalibrator` and its config constants/test wholesale (dead code, no more tap-to-
calibrate step anywhere), plus the now-unused `CircleRegion` (it only existed to describe the white-
sheet sample circle `ColorExtractor` excluded). `ColorExtractor.extract()` (candidate-list-with-share-
filter, `isClearlyDominant`) is replaced by a single `extractMainColor(pixels, region = centerBox)` -
quantizes with the same Celebi quantizer and returns the single largest-share `argb`, no `Double?`
share or candidate list to plumb through. `RectRegion.centerBox(width, height, fraction)` computes the
middle-40%-by-40% box (`CalibrationConfig.CENTER_BOX_FRACTION`); `CalibrationConfig` lost every
calibration/dominance/share-filter constant that only that old API used.

Both `MatchObjectViewModel` and `RateClothingViewModel` lost their `Calibrating`/`SelectingColor(s)`
states, `onTap`/`confirmCalibration`/`chooseNewPhoto`/(for Match Object)
`toggleColorSelection`/`confirmColorSelection` entirely. `onPhotoPicked` now decodes the bitmap, flips
to `ExtractingColors`, then a private `extractAndSaveResult(bitmap)` calls `extractMainColor` on
`backgroundDispatcher`, saves the history entry, and goes straight to `ShowingResult` - photo to result
in one step, no `currentBitmap` field needed since the bitmap is a local all the way through. Match
Object's `saveObjectResult` now always gets a single-element `inputColorsArgb` list; the stored field
name and repository signature are unchanged (still a `List<Int>`, per the AC - no migration).
`HarmonyResultBody` (shared by the live Match Object result and History detail) now takes one
`inputColorArgb: Int` instead of iterating a list, so `HistoryDetailScreen` passing
`entry.inputColorsArgb.first()` makes old multi-color entries display only their first color, satisfying
that AC without any data change.

Removed every white-sheet/calibration string (`rate_clothing_white_sheet_reminder`,
`_tap_white_sheet`, `_calibration_failed*`, `_confirm_calibration`, `_choose_different_photo`,
`_select_color`, `match_object_select_colors_title`, `match_object_continue`,
`settings_about_calibration` and its `AboutSection` line) and replaced the pick-photo reminder (shared
by both flows, as it already was) with a generic `pick_photo_reminder` that tells the user to center
the subject instead of mentioning a white sheet.

Test: rewrote `MatchObjectViewModelTest` around the new `extractAndSaveResult` (same off-main-thread
assertion shape as #20 - spinner shows before the background dispatcher is pumped, extraction runs on
the background dispatcher, then state lands on `ShowingResult`) with small local `Fake*` doubles for
`HistoryRepository`/`ThumbnailStore`/`SettingsRepository` (matching `HistoryViewModelTest`'s existing
fake-class style) rather than the old error-throwing `Proxy` stub, since this flow now actually reaches
the save step within the same coroutine. `ColorExtractorTest` rewritten for `extractMainColor`
(largest-share-in-box, out-of-box pixels ignored, explicit `region` override, single-color image).
Rate Clothing still has no dedicated ViewModel test (unchanged from #20). `./gradlew :colorspace:test
:app:testDebugUnitTest assembleDebug` all pass. Center-box overlay UI and in-app camera viewfinder are
out of scope here (issue #28).

## 2026-09-24 - Issue #20: Fix ANR - run color extraction off the main thread

`confirmCalibration` (Match Object and Rate Clothing) and `onTap` (white-balance sampling) now run
their pixel work inside `withContext(backgroundDispatcher)` (`Dispatchers.Default` by default,
injectable via the ViewModel constructor). `confirmCalibration` first sets a new `ExtractingColors`
UI state, which both screens render with the existing `LoadingStep()` spinner, then swaps to
SelectingColors/SelectingColor/result when extraction finishes. `onTap` updates state via
`_uiState.update` only if the same bitmap is still being calibrated. `ColorExtractor` now fills a
primitive `IntArray` (sized to the region, trimmed with `copyOf` if the exclusion circle skipped
pixels) instead of a boxed `ArrayList<Int>`. StrictMode thread policy (disk/network, log penalty) is
enabled in `HueAndYouApplication` only when `FLAG_DEBUGGABLE` is set.

Test: `MatchObjectViewModelTest` injects a `StandardTestDispatcher` as the background dispatcher
and checks that after `confirmCalibration()` the state is `ExtractingColors` and no pixel work has
run until the background dispatcher is pumped. `Bitmap` can't be built in plain JVM tests, so it's
allocated via Unsafe and the ViewModel gets a `pixelSourceOf` seam. Rate Clothing shares the same
pattern but has no dedicated test. PaletteImportViewModel has the same synchronous pattern and was
not touched (out of scope for #20). The on-device "no ANR with full-size photo" check is still manual.

## 2026-09-23 - Issue #17: Settings - About section with disclaimers and closeness bands

Added an "About these results" section to the bottom of `SettingsScreen` (`AboutSection`
composable, after the Backup section) - static explanatory text plus a dynamically-built list of
the four closeness bands. All disclaimer/explanation copy (how measurement works, the "best guess"
caveat, seasonal color analysis having little scientific backing, and the white-sheet calibration's
optical-brightener/lighting limits) lives in `strings.xml` as plain `settings_about_*` strings -
nothing there needed to be dynamic.

The band list is the one part the issue required to "never drift": each row is built from
`ColorMatchBand.MATCH_MAX_DELTA_E`/`CLOSE_MAX_DELTA_E`/`RELATED_MAX_DELTA_E` (the same constants
`PaletteScorer`/`ColorMatchBand.forDeltaE` already score against) rather than restating 3/8/15 as
literals in `strings.xml`, so a future change to those thresholds automatically updates this text.
Band labels reuse the existing `colorMatchBandLabel()` (from `PaletteResultView.kt`, already
`internal` and thus visible across `ui.*` packages in the app module) instead of adding parallel
`settings_about_band_*_label` strings - same label the Rate Clothing result screen already shows
for Match/Close/Related/Far. A small `formatDeltaE` helper trims the trailing `.0` off these
currently-whole-number `Double` constants (`3.0` -> "3") without hardcoding the assumption that
they'll always be whole numbers into the string resources themselves.

No new tests: this is static UI copy plus a read of existing, already-tested constants - no new
logic to unit-test, and this app has no Compose UI test harness (same Robolectric/JDK-26 gap noted
since #3). `./gradlew assembleDebug test` passes with no new failures.

## 2026-09-23 - Issue #16: JSON backup - export and import all data

New `data/backup/` package. `BackupSerializer` (`JsonBackupSerializer`) is a pure function
`BackupData <-> JSON` using kotlinx.serialization - no I/O, no DB/DataStore access - so every
validation rule (`ignoreUnknownKeys = true`; a missing required DTO field surfaces as
`SerializationException`; an unrecognized enum string or hex color throws) runs and can fail before
anything is written, satisfying "validation happens before any write" by construction rather than by
convention. `schemaVersion` is peeked from the raw `JsonElement` *before* the full `decodeFromString`,
so a newer/unrecognized version gets a clear "update the app" message instead of whatever generic
deserialization error the mismatched shape would otherwise produce. Colors are hex strings
(`colorspace`'s existing `formatHexColor`/`parseHexColor`, alpha-ignored, matching how the rest of
the app already treats color ints) rather than the domain's ARGB `Int`s, matching the PRD's
illustrative shape; a history entry's `clothing`/`object` (renamed `objectResult` + `@SerialName`
since `object` is reserved) blocks are mutually exclusive by `type`, validated on decode rather than
relying on the type system to enforce it.

`BackupRepository` (`DefaultBackupRepository`) is the I/O layer: exports by reusing the existing
`ProfileWithColors.toDomain()`/`HistoryEntryEntity.toDomain()` extensions (rather than re-deriving
`PaletteScore` from raw entity columns) plus `ThumbnailStore.readBytes` (new method - thumbnails were
previously only ever written by `Bitmap.compress`, never read back) for each entry's JPEG bytes,
base64-encoded into the JSON. Import deletes everything and reinserts under one `TransactionRunner`
(new indirection over `androidx.room.withTransaction` - added so this repository could be unit-tested
against the existing `FakeProfileDao`/`FakeHistoryDao` doubles, same as every other repository here,
rather than needing a real/Robolectric Room instance) - profile ids are remapped old-JSON-id ->
freshly-inserted-id as they're created, then substituted into each history entry's `profileId`, since
neither fake nor real Room insert can be trusted to reproduce the exact original row ids. New
thumbnail files are written *before* the transaction (pure, retryable) and the *old* ones are only
deleted *after* it commits, so a failed import never leaves History pointing at a missing file.
`ProfileDao`/`HistoryDao` gained bulk `deleteAll*`/`insert*(List<...>)` methods for this, mirrored in
both fakes.

`ui/settings/`: `SettingsViewModel` gained `exportBackup`/`importBackup` (`Result`-returning callback
style, since unlike every other action on this screen these two can fail in ways the user needs to
see). `SettingsScreen` gained a "Backup" section (Export/Import `TextButton`s) using
`ActivityResultContracts.CreateDocument`/`OpenDocument` for SAF - the first SAF usage in this app
(existing photo pickers all use `PickVisualMedia`/`TakePicture`, not document trees). Import reads
the chosen file to a `String`, then shows a confirm `AlertDialog` (same shape as
`delete_profile_dialog`) before calling into the ViewModel, since replacing all data can't be undone;
result/failure messages surface through a new `Scaffold`+`SnackbarHost` (same nested-Scaffold-for-
just-the-snackbar shape `HistoryScreen` already uses) - `BackupImportException.message` is written to
be shown directly, so the UI doesn't need its own copy of "what went wrong" strings.

New `BackupSerializerTest` (round-trip equality; unknown fields ignored; invalid JSON, a missing
required field, and a future schema version all throw `BackupImportException`) and
`DefaultBackupRepositoryTest` (export from one fake-backed repository into a second, fresh one -
profile/color ids line up because both start empty and are filled in the same order, but history ids
don't, since export orders by `createdAt DESC` while re-insertion replays that order into an
originally-empty table - `id`/`thumbnailPath` are normalized away before comparing since they're
storage details, not dataset content; a separate assertion confirms thumbnail bytes carried over
correctly via the fakes' own paths). `BackupHistoryEntry` needed hand-written `equals`/`hashCode`
(the `ByteArray` thumbnail field breaks the data class default, which compares by identity).

`./gradlew assembleDebug test` passes (8 new test cases: 5 `BackupSerializerTest`, 3
`DefaultBackupRepositoryTest`). No UI test for the Export/Import buttons or the confirm dialog (same
Robolectric/JDK-26 gap noted since #3) - verified by reading through the SAF launcher wiring and by
the fact the confirm dialog reuses `delete_profile_dialog`'s already-working `AlertDialog` shape.
