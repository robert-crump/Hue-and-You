## 2026-09-23 - Issue #9: History - auto-save clothing results, list and reopen

New `data/history` package (`:app`): `HistoryEntryEntity` (Room, table `history_entries`, no FK to
`profiles` - deliberately, since AC requires a profile's History entries to stay readable after
that profile is deleted) stores the snapshot as plain columns rather than reusing `:colorspace`'s
`PaletteScore`/`ColorMatch` domain types directly, matching the existing "primitives at the module
boundary" pattern (`nearestBestArgb`/`nearestBestDeltaE`/etc, nullable in pairs; `ColorMatchBand` is
recomputed from `deltaE` via `ColorMatchBand.forDeltaE` on read rather than stored, since it's a
pure function of the ΔE already saved - one less thing to keep in sync). `bestColorsArgb`/
`avoidColorsArgb` (the profile's Best/Avoid lists *at save time*) round-trip through a new
`HistoryConverters` as a comma-joined string - plain values, no JSON library needed since these are
just `List<Int>`. `HistoryEntry` (domain) holds a real `score: PaletteScore`, reconstructed by
`HistoryEntryEntity.toDomain()`; `:app` can freely reference `:colorspace` types (only the reverse
direction is restricted), so this doesn't fight the module boundary the way storing them by-value
does above.

`HistoryRepository.saveClothingResult(thumbnailPath: String, calibratedArgb, profile: Profile?,
score: PaletteScore)` takes an already-saved thumbnail *path*, not a `Bitmap` - keeps
`DefaultHistoryRepository` fully unit-testable with `FakeHistoryDao` (same in-memory-map-plus-
`MutableStateFlow` shape as `FakeProfileDao`) with zero Android framework dependency, since this
repo's app-module unit tests can't touch `android.graphics.*` (Robolectric/JDK-26 limitation, noted
since the #3 entry). The actual Bitmap -> downscaled-JPEG-in-`filesDir` work lives in a separate
`ThumbnailStore`/`FileThumbnailStore` (512px long edge, `context.filesDir/history_thumbnails/`,
`Dispatchers.IO`) that `RateClothingViewModel` calls directly before handing the resulting path to
the repository - not verified by a JVM unit test for the same Bitmap-can't-be-constructed reason as
`ThumbnailStore`'s Android-framework siblings elsewhere in the app, verified by reading through it
instead. Default name is "type + date/time" (`defaultHistoryEntryName`, e.g. "Clothing Sep 23, 2026
3:45 PM") via `java.time` (`minSdk 37`, no desugaring needed).

`HueAndYouDatabase` bumped to version 2 (new `HistoryEntryEntity` + `historyDao()`); `AppContainer`'s
`Room.databaseBuilder` now calls `.fallbackToDestructiveMigration(dropAllTables = true)` since there's
no shipped install base yet to write a real migration for.

`:app` wiring: `RateClothingViewModel` gained `historyRepository`/`thumbnailStore` (both from
`AppContainer`, same factory pattern as `profileRepository`) and a `currentBitmap` field (set in
`onPhotoPicked`, independent of the UI state machine) since the color-selection step
(`SelectingColor`) doesn't itself carry the original bitmap. `confirmCalibration()`'s
clearly-dominant path and `selectColor()` now funnel through `showResult(argb)`, which computes the
`PaletteScore` synchronously (unchanged logic, renamed from the old `resultFor` to `scoreFor`) but
saves to History inside a `viewModelScope.launch` (thumbnail encode + Room insert are real I/O) -
`ShowingResult` only appears once the entry is saved and has its id/name, so by the time a result is
on screen it's already persisted; `RateClothingUiState.ShowingResult` gained `historyEntryId`/
`historyEntryName` fields for this. `renameResult(name)` on the ViewModel persists a rename via
`historyRepository.renameEntry`.

UI: extracted the swatch/hex/closer-to-avoid-warning/ΔE-rows/disclaimer block out of
`RateClothingScreen.kt`'s old private `ResultStep` into a new `ui/common/PaletteResultView.kt`
(`internal` visibility - shared module-wide, not truly public) as `PaletteResultBody`, since both
the live Rate Clothing result step and the new History detail screen need to render the exact same
content from a `PaletteScore` snapshot. `ResultStep` now also has an `OutlinedTextField` for the
name (`rememberSaveable` keyed on `entryId`, same "local state + call the ViewModel on each edit"
pattern `ProfileEditorScreen`'s name field already uses, to avoid Flow round-trip cursor jumps).

New `ui/history/`: `HistoryViewModel` now exposes real `observeEntries()` data instead of a stub;
`HistoryScreen` renders a `LazyColumn` of rows (thumbnail decoded off the main thread via
`produceState` + `BitmapFactory.decodeFile`, name, "type · profile name" subtitle, formatted date),
tappable into a new `Destination.HistoryDetail` route / `HistoryDetailScreen` +
`HistoryDetailViewModel`, which observes one entry by id and reuses `PaletteResultBody` plus the
same editable-name field - "reopening" is just rendering the saved snapshot's `calibratedArgb`/
`score`, so it's naturally unaffected by later profile edits or deletion (nothing re-reads
`ProfileRepository`).

New tests: `FakeHistoryDao` + `DefaultHistoryRepositoryTest` (default name format, profile/score
snapshot fields with and without a profile, newest-first ordering, rename persists, and an explicit
test that mutating a `Profile` object after saving doesn't touch the already-stored snapshot).

`./gradlew assembleDebug test` passes (6 new `DefaultHistoryRepositoryTest` cases). No UI/
instrumented test for the History list/detail screens or thumbnail file I/O (same Robolectric/
JDK-26 limitation noted since the #3 entry) - verified by reading through the Compose tree and
repository wiring instead. Verified no new manifest permissions were introduced (no manifest
changes in this issue).

## 2026-09-23 - Issue #8: Rate clothing - profile selection, PaletteScorer and result screen

Closed the loop on the Rate Clothing flow: profile choice at the start, scoring the measured
color against that profile, and a real result screen (replacing the old "swatch + hex" stub
from issue #5).

`PaletteScorer` (new, `:colorspace`, pure Kotlin): `PaletteScorer.score(measuredArgb,
bestColors, avoidColors)` takes plain `List<Int>` ARGB lists rather than the app module's
`Profile`/`PaletteColor` domain types - `:colorspace` is a pure-JVM module and can't depend on
`:app`, matching the existing `ColorExtractor`/`WhiteBalanceCalibrator` pattern of talking in
primitives at the module boundary. Converts the measured color to Lab once and finds each
side's nearest match by ΔE00 (`ciede2000`, from issue #2); either side is `null` when its list
is empty, and `closerToAvoid` is only ever true when *both* sides have a match and Avoid's ΔE
is strictly smaller - an empty Best list can't make "closer to Avoid" true by default, since
there's nothing to be closer *than*. Bands live in a new `ColorMatchBand` enum with the
boundary constants and the classifying function on its companion, in the same file as
`PaletteScorer` - "one place" per the issue, and colocated rather than folded into
`CalibrationConfig` since these thresholds are about matching against a profile, not about
calibration/extraction. Boundaries per the issue's own numbers: ΔE ≤ 3 match, ≤ 8 close, ≤ 15
related, > 15 far (all inclusive at the upper edge, tested directly at each boundary value).

`:app` wiring: `RateClothingViewModel` now takes a `ProfileRepository` (via the same
`companion object factory(context)` + `viewModelFactory { initializer { ... } }` pattern
`ProfilesViewModel`/`ProfileEditorViewModel` already use) and starts in a new
`LoadingProfiles` state. `init` reads `observeProfiles().first()` once (a snapshot for this
rating session, not a live subscription - the profile list isn't expected to change mid-flow)
and branches to `NoProfile`, or straight past selection into `PickingPhoto` with
`selectedProfile` set when there's exactly one profile, or `SelectingProfile(profiles)` when
there are several; `selectProfile(profile)` (called on user tap) does the same
"stash-then-advance-to-PickingPhoto" transition. Both `confirmCalibration()`'s
clearly-dominant path and `selectColor()` now funnel through a shared `resultFor(argb)` that
runs `PaletteScorer.score` against the stashed `selectedProfile` (or an all-null/false
`PaletteScore` if somehow still unset) and produces `ShowingResult(argb, score)` -
`RateClothingUiState.ShowingResult` gained that `score: PaletteScore` field.

UI (`ui/rateclothing/RateClothingScreen.kt`): `NoProfile` renders an `AlertDialog` (title +
body + "Cancel"/"Go to Settings" buttons, both dismissing) rather than a full screen, since the
issue frames it as a dialog, not a step; "Cancel" reuses the screen's existing
`onNavigateBack`, and the new `onNavigateToProfileSettings` callback (screen gained this
parameter) is wired in `HueAndYouNavHost` to `Destination.Settings.route(scrollToProfiles =
true)` - the deep-link route issue #3 built for exactly this. `SelectingProfile` is a plain
tappable name list, matching the existing `SelectingColorStep` list pattern. `ResultStep` now
shows the measured swatch+hex (unchanged from before, just relabeled), then an error-colored
"closer to Avoid" warning when `score.closerToAvoid`, then a `ColorMatchRow` (swatch + hex + "ΔE
x.x — <band>") for each of `nearestBest`/`nearestAvoid` that isn't null, then the "best guess"
disclaimer at the bottom - the whole column is now `verticalScroll`-wrapped since this can run
longer than one screen on small devices. Band labels are their own four string resources
(`color_match_band_*`) via a small `colorMatchBandLabel` mapping function, same shape as the
existing `calibrationFailureMessage` mapping for `WhiteBalanceFailureReason`.

New tests: `PaletteScorerTest` (`:colorspace`) - band boundaries at each threshold edge,
nearest-color selection among several candidates, `closerToAvoid` true/false in both
directions, and all three empty-list combinations (empty Best, empty Avoid, both empty).

`./gradlew assembleDebug test` passes (7 new `PaletteScorerTest` cases). No UI/instrumented
test for the profile dialog/list taps or the result screen layout itself (same
Robolectric/JDK-26 limitation noted in the #3 entry, and still no emulator/device available in
this environment) - verified by reading through the state machine and Compose tree instead.
Verified no new manifest permissions were introduced (no manifest-affecting changes in this
issue).

## 2026-09-23 - Issue #7: Camera capture as photo source

Added "Take photo" alongside the existing gallery picker on `PickPhotoStep` (`:app`,
`ui/rateclothing/RateClothingScreen.kt`) - no custom in-app camera, per the issue, just the
system camera app via the standard `ActivityResultContracts.TakePicture()` contract, which
(unlike `TakePicturePreview()`) writes the full-resolution photo to a URI instead of handing
back a small thumbnail `Bitmap` - full resolution matters here since the same photo is later
sampled pixel-by-pixel for white-balance calibration and dominant-color extraction.

`TakePicture()` needs a destination `content://` URI up front, which needs a `FileProvider`:
added `androidx.core.content.FileProvider` to `AndroidManifest.xml` (authority
`${applicationId}.fileprovider`, `exported="false"`, `grantUriPermissions="true"`) plus
`res/xml/file_paths.xml` declaring one `cache-path` (`camera_captures/`). No new runtime
permission needed - launching the system camera via an implicit `TakePicture` intent doesn't
require `android.permission.CAMERA` (that's only for apps driving the camera hardware
directly via camera2/CameraX), confirmed by diffing the merged manifest before/after: the
only addition is the `<provider>` entry itself.

`createCameraPhotoUri()` (in `RateClothingScreen.kt`, next to `PickPhotoStep` since it needs
a live `Context`) creates a fresh temp file under `cacheDir/camera_captures/` per capture
attempt and wraps it via `FileProvider.getUriForFile`. The screen holds the pending URI in
`remember { mutableStateOf<Uri?>(null) }` since the `TakePicture()` callback only receives a
`Boolean` success flag, not the URI itself - on `success == true` it's handed to the existing
`viewModel.onPhotoPicked(contentResolver, uri)`, the same entry point the gallery picker
already uses, so the ViewModel needed zero changes (it already treats "photo" as "some URI I
can open via `ContentResolver`", regardless of source). On cancel (`success == false`) the
pending URI is just dropped and the screen stays on `PickingPhoto` - satisfies "cancelling
the camera returns to the photo step without error" for free, no new state needed.

`PickPhotoStep` now takes both `onTakePhoto` and `onPickPhoto` and shows both buttons
unconditionally, so `RateClothingViewModel.chooseNewPhoto()` (the "choose a different photo"
recovery path added in issue #6) automatically offers the camera too, since it just resets
back to the same `PickingPhoto` state - no separate wiring needed for that acceptance
criterion either. Renamed the existing gallery-pick string (`rate_clothing_pick_photo`,
"Choose photo" -> "Pick from gallery") and added `rate_clothing_take_photo` ("Take photo") to
match the issue's own button wording.

`./gradlew assembleDebug test` passes (no new unit tests - this is compose UI wiring over
Android framework classes, `ContentResolver`/camera intents/`FileProvider`, same
Robolectric/JDK-26 limitation noted in the #3 entry, and still no emulator/device available
in this environment to exercise it end to end). Verified via merged-manifest diff that the
only new manifest content is the `FileProvider` `<provider>` entry - no new permissions.

## 2026-09-23 - Issue #6: Calibration failures - clipped, too dark, not white

Added real failure *detection* to `WhiteBalanceCalibrator.calibrate` in `:colorspace` (issue #5
only guarded the zero-sampled-pixels edge case; this issue is the "that patch wasn't actually
white/gray" detection deferred there). Three new `WhiteBalanceFailureReason` values, checked in
this order after the existing `NO_SAMPLED_PIXELS` guard:
- `CLIPPED`: while summing the sample circle's pixels, also counts pixels with any raw channel
  (0-255 scale, not linear) at/above `CalibrationConfig.CLIPPED_CHANNEL_THRESHOLD` (250). Fails
  once that count's share of the sample exceeds `CLIPPED_PIXEL_FRACTION_THRESHOLD` (0.05) - both
  are the issue's own starting-guess numbers.
- `TOO_DARK`: converts the sample's averaged linear RGB to Lab and fails if `L` is below
  `MIN_WHITE_LUMINANCE_L` (50.0, a starting guess - a lit white sheet should read far brighter
  than mid-gray).
- `NOT_WHITE`: fails if that same Lab point's chroma (`sqrt(a^2+b^2)`) exceeds
  `MAX_WHITE_CHROMA` (15.0, a starting guess) - reuses `linearRgbToLab` from issue #2, no new
  color math needed.
All four thresholds are `CalibrationConfig` consts, each also a `calibrate(...)` default
parameter (same pattern as the existing `sampleRadiusFraction`), so tests can override
individually. Picked the threshold values against the actual Lab math (via a throwaway Python
port of the sRGB->Lab constants, checked against `ColorConversions.kt` line for line) rather
than guessing blind, so the existing "warm-tinted white" happy-path test and the three new
failure tests all land with real margin, not by luck.

Had to retune the existing `warmTintedWhitePatchIsCorrectedToNeutral` test fixture: its old
color (`0xFFFFE0C0`, R=255) was itself clipped and had chroma ~20 - both of which now correctly
fail before this issue, since nothing previously checked for either. Swapped it for a milder
warm off-white (`0xFFF5E6D3`, L~92, chroma~11) that's still clearly warm-tinted but comfortably
inside both new thresholds - this is a fixture fix caused by adding real detection, not a
weakening of the test.

UI (`:app`, `ui/rateclothing/`): `CalibratingStep`'s failure `Text` now switches on
`WhiteBalanceFailureReason` to one of four distinct string resources (clipped/too-dark/not-white
messages, plus the existing generic one for `NO_SAMPLED_PIXELS`) instead of one generic message
for every failure. Added a second button, "Choose a different photo"
(`RateClothingViewModel.chooseNewPhoto()` resets to `PickingPhoto`), next to the existing
Continue button - re-tapping already worked for free (the photo stays on screen and `onTap` just
overwrites `calibration`), so this covers the acceptance criterion's other half ("re-tap or
choose a new photo") without new state-machine states.

`./gradlew assembleDebug test` passes (3 new calibrator failure tests, 1 existing test fixture
retuned). Verified no new manifest permissions were introduced.

## 2026-09-23 - Issue #5: Calibrate and extract - white-sheet tap and dominant colors (happy path)

Built the deep logic in `:colorspace` (pure Kotlin, so it's fully unit-testable without a
device/emulator) plus the UI wiring in `:app` that replaces the old Rate Clothing placeholder.

`:colorspace` additions:
- `PixelSource` (interface: `width`/`height`/`pixelAt`) decouples the calibration/extraction
  math from `android.graphics.Bitmap` - `:colorspace` is a pure-JVM module and can't reference
  Android framework classes. `IntArrayPixelSource` is the flat-array implementation, used
  directly by tests and (via `:app`'s new `Bitmap.toPixelSource()` extension, which bulk-copies
  via `getPixels` rather than a slow pixel-by-pixel `getPixel` loop) by the real screen.
- `WhiteBalanceCalibrator.calibrate(pixels, tapX, tapY)` samples a circular patch (radius =
  `CalibrationConfig.WHITE_SAMPLE_RADIUS_FRACTION` of the image's short edge) in linear RGB,
  averages each channel, and returns a `WhiteBalanceCorrection` (per-channel scale factors) that
  maps that average to neutral gray - a diagonal, von-Kries-style correction, not a full CAT
  matrix, since the issue only asked for RGB channel scaling. Returns a sealed
  `WhiteBalanceResult` (`Success`/`Failure`); the only failure case wired up is "tap landed where
  the sample circle has zero in-bounds pixels" - real failure *detection* (e.g. "that patch
  wasn't actually white/gray") is explicitly a separate issue, so `Failure` only guards the
  divide-by-zero/out-of-bounds edge case for now.
- `ColorExtractor.extract(pixels, correction?, region?, exclusion?)` crops (optional
  `RectRegion`), skips an optional `CircleRegion` (the white-sample patch), applies the
  correction, and quantizes via `QuantizerCelebi` (Wu boxes + weighted k-means) from the
  `material-color-utilities` dependency already in the version catalog - this is the same
  quantizer Material You uses for wallpaper theming, and matches the issue's "MCU (Celebi)"
  wording exactly, so no new dependency was needed. Colors below `MIN_COLOR_SHARE` are dropped
  and the list is capped at `MAX_COLORS`; "clearly dominant" (`DOMINANT_MIN_SHARE` and
  `DOMINANT_MIN_RATIO_TO_RUNNER_UP`) is computed from the *unfiltered* sorted list so a
  runner-up that gets dropped by the share filter can't accidentally make a borderline top
  color look more dominant than it is.
- All six thresholds live in one `CalibrationConfig` object (const vals), each also exposed as
  a default parameter on `calibrate`/`extract` so tests can override individual values without
  touching global state.
- New tests: `WhiteBalanceCalibratorTest` (warm-tinted synthetic white patch corrects to
  R=G=B; tap fully outside the image fails cleanly) and `ColorExtractorTest` (two solid regions
  return both colors at ~50/50 share; a solid image is flagged clearly-dominant at 100% share;
  an excluded circular region's color never appears in the result, verified by filling that
  region with a color - white - that would otherwise clear the share threshold).

`:app` (`ui/rateclothing/`, replacing `RateClothingPlaceholderScreen.kt`): `RateClothingScreen`
is a state machine (`RateClothingUiState`: `PickingPhoto` -> `LoadingPhoto` -> `Calibrating` ->
`SelectingColor` or straight to `ShowingResult` if clearly dominant). Photo selection uses the
system Photo Picker (`ActivityResultContracts.PickVisualMedia`, no runtime permission needed).
The picked photo is decoded via `ImageDecoder` with `ALLOCATOR_SOFTWARE` (hardware bitmaps can't
do pixel readback) and downscaled to a max 1024px side (`MAX_PHOTO_DIMENSION_PX`) so calibration/
extraction stay fast on full-resolution camera photos - this is a practical decode-time concern,
not one of the domain thresholds, so it's a local constant in the ViewModel rather than added to
`CalibrationConfig`. The image is displayed at its exact aspect ratio (`Modifier.aspectRatio`)
so tap coordinates scale linearly to bitmap pixels with no letterboxing math. Re-tapping just
re-runs calibration and overwrites the previous result; the "Continue" button is only enabled
once `calibration` is a `Success`, which is what enforces "extraction cannot run before a
successful calibration" - confirmCalibration() also independently guards on the same cast, so a
future caller of the ViewModel can't bypass it either. The clothing-result screen (matching
against a saved profile) is out of scope here per the issue - `ShowingResult` just shows the
calibrated swatch and its hex.

`./gradlew assembleDebug test` passes. No UI/instrumented test for the tap gesture or Photo
Picker flow itself (same Robolectric/JDK-26 limitation noted in the #3 entry, and still no
emulator/device available in this environment) - verified by reading through the gesture math
and state transitions instead. Verified no new manifest permissions were introduced.
