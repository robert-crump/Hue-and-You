## 2026-09-23 - Issue #3: Profiles (create, rename, delete, add/remove colors by hex)

Wired up Room for the first time (deferred from issue #1/#2). Used **KSP**, not kapt:
tested `com.google.devtools.ksp` against this repo's Kotlin 2.4.20 even though the KSP
plugin portal's newest published pairing is `2.3.12` (KSP has apparently decoupled its own
versioning from a strict per-Kotlin-version pairing as of its 2.3.x line) - `:app:kspDebugKotlin`
and a full `assembleDebug test` both succeeded, so this is confirmed working, not just
theorized. Added `libs.plugins.ksp` (root `build.gradle.kts` applies it `apply false`,
`:app` applies it for real) and `ksp(libs.androidx.room.compiler)`.

Data layer lives under `com.example.hueandyou.data.profile` in `:app` (needs a live
Android `Context` for `Room.databaseBuilder`, so it couldn't go in the pure-JVM
`:colorspace` module):
- `ProfileEntity` / `PaletteColorEntity` (`Room`, FK cascade-delete from profile to its
  colors) + `Converters` (ColorKind <-> String) + `ProfileWithColors` (`@Relation`).
- `ProfileDao`: flows for the profile list and a single profile-with-colors, plus
  suspend CRUD; `nextPosition(profileId, kind)` computes the next append position so Best
  and Avoid colors keep independent, stable orderings.
- `ProfileRepository` (interface) / `RoomProfileRepository` (impl): the only place that
  knows about Room - it maps `ProfileWithColors` to the plain `Profile`/`PaletteColor`
  domain types the UI sees, splitting/sorting colors by kind+position. Timestamps come
  from an injectable `currentTimeMillis: () -> Long` (defaults to `System::currentTimeMillis`)
  specifically so tests can control `createdAt`/`updatedAt` deterministically.
- `AppContainer`/`DefaultAppContainer` now also builds the (lazy, singleton) `RoomDatabase`
  and exposes `profileRepository`.

UI: `SettingsScreen` now renders a "Profiles" `LazyColumn` section (header + add button +
per-profile cards with name and Best-color swatches) instead of the old placeholder text;
`ProfileEditorScreen` (new) has the name field, two color sections (Best / Avoid) each with
an add-by-hex dialog (validated via `colorspace.parseHexColor`, inline error on bad input)
and a per-color remove button, plus a delete-profile flow gated by an `AlertDialog`
confirmation. Both screens get their ViewModel via a small `viewModelFactory { initializer
{ ... } }` companion function that reaches into `HueAndYouApplication.container` - this
project still has no DI framework, so this is the established manual-DI pattern going
forward for any screen needing repository access (`SettingsViewModel` placeholder class
was deleted, replaced by `ProfilesViewModel`).

Navigation: `Destination.Settings` route gained an optional `scrollToProfiles` bool query
arg (`Destination.Settings.route(scrollToProfiles = true)`) so other screens can deep-link
into Settings pre-scrolled to the Profiles section (this is what issue #8's "no profile"
dialog on Rate Clothing will need - not built here, just the addressable route + the
`LaunchedEffect` that calls `listState.animateScrollToItem(0)` when the flag is set).
Added `Destination.ProfileEditor` (`profile_editor/{profileId}`, `NavType.LongType`).
Important: `TopLevelDestination` needed a separate `navRoute` field from `destination.route`
- the latter is the *template* string (with `{scrollToProfiles}` literally in it) used to
register the composable, and is not itself a navigable route once a destination takes args.

Testing gotcha worth recording: tried Robolectric (`4.17`) for a real in-memory-SQLite Room
DAO test first, since that would exercise the actual `@ForeignKey`/`@Relation` annotations
end to end. It failed hard on this machine's JDK (Gradle's launcher/toolchain JVM is 26.0.1)
with `IllegalAccessException: module java.base does not export jdk.internal.access` inside
Robolectric's `FileDescriptorInterceptor` - a JDK-internals shim Robolectric 4.17 doesn't yet
support on JDK 26. Rather than fight `--add-opens` flags for an unsupported JDK/Robolectric
combination, switched to a hand-written `FakeProfileDao` (in-memory, implements the real
`ProfileDao` interface) and tests `RoomProfileRepository` against that - this covers the
repository's own logic (timestamping, position assignment, kind-splitting, mapping to domain
types) but does NOT verify Room's own cascade-delete/relation-query behavior against real
SQLite. If a future issue needs that guarantee, it'll need either an instrumented test
(`connectedAndroidTest`, needs a device/emulator - none available in this environment) or a
retry of Robolectric once it/the JDK situation here changes.

`./gradlew assembleDebug test` passes (7 new tests: 5 repository, 2 ViewModel hex/delete
logic). Verified no new permissions in the merged manifest.

## 2026-09-23 - Issue #2: ColorSpace module (conversions, CIEDE2000, hex parsing)

Added a new `:colorspace` Gradle module: pure-Kotlin JVM (org.jetbrains.kotlin.jvm plugin,
no AGP, no Android dependency), so this module is a plain JAR consumable outside the app
too. Public API lives in package com.example.hueandyou.colorspace:
- LinearRgb / Lab / Hct: immutable data classes (Lab and linear RGB on the CIE 0-100 scale,
  not 0-1, so they line up with Y = relative luminance and with the white point).
- argbToLinearRgb/linearRgbToArgb, linearRgbToLab/labToLinearRgb, argbToLab/labToArgb,
  argbToHct/hctToArgb: sRGB math (companding, D65 sRGB<->XYZ matrices, CIE 1976 Lab
  piecewise f/f-inverse) is implemented directly in this module; HCT is NOT reimplemented -
  it delegates to Material Color Utilities' Hct.fromInt/Hct.from/toInt (moved the
  `material-color-utilities` dependency from :app to :colorspace, :app now depends on
  :colorspace via `implementation(project(":colorspace"))` and no longer touches MCU
  directly).
- ciede2000(Lab, Lab): Double - full Sharma/Wu/Dalal (2005) ΔE00 formula.
- parseHexColor(String): Int? / formatHexColor(Int): String - `#RRGGBB`/`RRGGBB`,
  case-insensitive in, `#RRGGBB` uppercase out; alpha is ignored on format and forced to
  0xFF on parse.

Verified CIEDE2000 against the actual published 34-pair Sharma/Wu/Dalal reference table
(fetched from the paper author's site, not reconstructed from memory) - all 34 pairs match
to the table's own 4-decimal precision. Round-trip tests (srgb->linear->srgb,
srgb->lab->srgb, srgb->hct->srgb) run over a fixed set of primaries/secondaries/grays/
arbitrary colors rather than randomized input, to keep the suite deterministic.

Added the `kotlin-jvm` plugin alias to libs.versions.toml/root build.gradle.kts (`apply
false` at root, applied for real in colorspace/build.gradle.kts) - this is unrelated to
and not blocked by the AGP-built-in-Kotlin gotcha below, since that gotcha only affects
Android (AGP) modules; a non-Android module still needs the ordinary Kotlin JVM plugin.

`./gradlew assembleDebug test` (root) and `./gradlew :colorspace:test` both pass.

## 2026-09-23 - Issue #1: App shell (navigation, dynamic color, History empty state, FAB)

Implemented the runnable app shell:
- Wired the agreed stack: Compose + Material3, Navigation Compose, Room (runtime/ktx only,
  no KSP/compiler yet - no entities exist), kotlinx.serialization, DataStore (preferences),
  and Material Color Utilities (me.tatarka.google.material:material-color-utilities, the
  only real Maven Central artifact for the Java port of Google's library).
- Added HueAndYouApplication + a manual DI AppContainer (holds a DataStore<Preferences>).
- MainActivity hosts a NavHost with History and Settings bottom-nav destinations, plus two
  placeholder destinations ("Rate clothing", "Match colors for an object") reached from a
  FAB dropdown menu on the History tab.
- Theme.kt uses dynamicLightColorScheme/dynamicDarkColorScheme (device is always API 31+,
  so dynamic color is unconditionally available) with a static fallback.
- History screen shows an empty state (icon + title + explanatory body text).
- Removed the legacy View-based Material Components theme/colors.xml since the app is
  Compose-only now.

Key gotcha for future issues: this repo's AGP (9.2.1) has *built-in* Kotlin support - do
NOT apply the `org.jetbrains.kotlin.android` plugin, it now fails the build outright
("no longer required for Kotlin support since AGP 9.0"). Only apply
`org.jetbrains.kotlin.plugin.compose` / `.plugin.serialization` when needed, version-pinned
via libs.versions.toml (kotlin = "2.4.20"). Also: androidx.compose.material3.TopAppBar is
still `@ExperimentalMaterial3Api` on the compose-bom version in use (2026.09.00) - needs
`@OptIn(ExperimentalMaterial3Api::class)`.

`./gradlew assembleDebug test` passes. Verified no INTERNET permission in the merged
manifest. Room's compiler/KSP setup is deliberately deferred to whichever issue first adds
a real @Entity/@Dao (likely issue #9, History auto-save) - wiring KSP now without any
annotated classes to process would add unverified version-matching risk for no benefit.
