## 2026-09-23 - Issue #16: JSON backup - export and import all data

New `data/backup/` package. `BackupSerializer` (`JsonBackupSerializer`) is a pure function
`BackupData <-> JSON` using kotlinx.serialization - no I/O, no DB/DataStore access - so every
validation rule (`ignoreUnknownKeys = true`; a missing required DTO field surfaces as
`SerializationException`; an unrecognized enum string or hex color throws) runs and can fail before
anything is written, satisfying "validation happens before any write" by construction rather than by
convention. `schemaVersion` is peeked from the raw `JsonElement` *before* the full `decodeFromString`,
so a newer/unrecognized version gets a clear "update the app" message instead of whatever generic
deserialization error the mismatched shape would otherwise produce. Colors are hex strings
(`colorspace`'s existing `formatHexColor`/`parseHexColor`, alpha-ignored, matching how the rest of
the app already treats color ints) rather than the domain's ARGB `Int`s, matching the PRD's
illustrative shape; a history entry's `clothing`/`object` (renamed `objectResult` + `@SerialName`
since `object` is reserved) blocks are mutually exclusive by `type`, validated on decode rather than
relying on the type system to enforce it.

`BackupRepository` (`DefaultBackupRepository`) is the I/O layer: exports by reusing the existing
`ProfileWithColors.toDomain()`/`HistoryEntryEntity.toDomain()` extensions (rather than re-deriving
`PaletteScore` from raw entity columns) plus `ThumbnailStore.readBytes` (new method - thumbnails were
previously only ever written by `Bitmap.compress`, never read back) for each entry's JPEG bytes,
base64-encoded into the JSON. Import deletes everything and reinserts under one `TransactionRunner`
(new indirection over `androidx.room.withTransaction` - added so this repository could be unit-tested
against the existing `FakeProfileDao`/`FakeHistoryDao` doubles, same as every other repository here,
rather than needing a real/Robolectric Room instance) - profile ids are remapped old-JSON-id ->
freshly-inserted-id as they're created, then substituted into each history entry's `profileId`, since
neither fake nor real Room insert can be trusted to reproduce the exact original row ids. New
thumbnail files are written *before* the transaction (pure, retryable) and the *old* ones are only
deleted *after* it commits, so a failed import never leaves History pointing at a missing file.
`ProfileDao`/`HistoryDao` gained bulk `deleteAll*`/`insert*(List<...>)` methods for this, mirrored in
both fakes.

`ui/settings/`: `SettingsViewModel` gained `exportBackup`/`importBackup` (`Result`-returning callback
style, since unlike every other action on this screen these two can fail in ways the user needs to
see). `SettingsScreen` gained a "Backup" section (Export/Import `TextButton`s) using
`ActivityResultContracts.CreateDocument`/`OpenDocument` for SAF - the first SAF usage in this app
(existing photo pickers all use `PickVisualMedia`/`TakePicture`, not document trees). Import reads
the chosen file to a `String`, then shows a confirm `AlertDialog` (same shape as
`delete_profile_dialog`) before calling into the ViewModel, since replacing all data can't be undone;
result/failure messages surface through a new `Scaffold`+`SnackbarHost` (same nested-Scaffold-for-
just-the-snackbar shape `HistoryScreen` already uses) - `BackupImportException.message` is written to
be shown directly, so the UI doesn't need its own copy of "what went wrong" strings.

New `BackupSerializerTest` (round-trip equality; unknown fields ignored; invalid JSON, a missing
required field, and a future schema version all throw `BackupImportException`) and
`DefaultBackupRepositoryTest` (export from one fake-backed repository into a second, fresh one -
profile/color ids line up because both start empty and are filled in the same order, but history ids
don't, since export orders by `createdAt DESC` while re-insertion replays that order into an
originally-empty table - `id`/`thumbnailPath` are normalized away before comparing since they're
storage details, not dataset content; a separate assertion confirms thumbnail bytes carried over
correctly via the fakes' own paths). `BackupHistoryEntry` needed hand-written `equals`/`hashCode`
(the `ByteArray` thumbnail field breaks the data class default, which compares by identity).

`./gradlew assembleDebug test` passes (8 new test cases: 5 `BackupSerializerTest`, 3
`DefaultBackupRepositoryTest`). No UI test for the Export/Import buttons or the confirm dialog (same
Robolectric/JDK-26 gap noted since #3) - verified by reading through the SAF launcher wiring and by
the fact the confirm dialog reuses `delete_profile_dialog`'s already-working `AlertDialog` shape.

## 2026-09-23 - Issue #15: Share card - PNG palette card via share sheet

New `data/share/ShareCardRenderer.kt`: `ShareCardRenderer` interface plus `FileShareCardRenderer`,
following the same shape as `ThumbnailStore`/`FileThumbnailStore` - a `Context`-holding class with
one suspend entry point (`render(profile): Uri`) that does its work on `Dispatchers.IO`. Drawing is
plain `android.graphics.Canvas`/`Paint` (not Compose - there's no Compose-to-Bitmap rasterizer in
this codebase, and the issue's output is a raster PNG anyway), sized in two passes: paints are built
first (title/section/hex/empty, all independent of any `Canvas`), their `fontMetrics` measure the
exact height each block needs, *then* the bitmap is allocated at that computed height - so
`drawSection`'s own layout math (`sectionContentHeight`, shared between the pre-measure sum and the
actual per-swatch draw loop) is the single source of truth for vertical space, rather than two
formulas that could drift apart. Empty Best/Avoid lists (the "any profile" AC) render the section
header plus the existing `profile_editor_no_colors` string instead of a swatch grid - reusing that
string (and `profile_editor_best_colors_title`/`_avoid_colors_title`) rather than adding parallel
`share_card_*` copies, since the card's sections are meant to read identically to the editor's.
Hex labels under each swatch reuse `colorspace`'s `formatHexColor` (already used by
`ProfileEditorScreen`), not a new formatter. The PNG goes to a new `cache/share_cards/` dir (new
`file_paths.xml` `cache-path` entry alongside the existing `camera_captures` one) and out through the
same `androidx.core.content.FileProvider` authority `RateClothingScreen`'s camera-capture flow
already registers in the manifest - no new provider needed, since a `FileProvider` authority isn't
tied to one specific source directory.

`AppContainer` gained `shareCardRenderer: ShareCardRenderer` (same `by lazy { ... }` pattern as
`thumbnailStore`). `ProfilesViewModel` gained the `ShareCardRenderer` dependency and a
`shareCard(profile, onRendered)` that launches the render in `viewModelScope` and hands the
resulting `Uri` back via callback - `SettingsScreen` already held the only `ProfilesViewModel`
instance backing the profile cards, so this was the natural place rather than a new ViewModel just
for sharing.

UI: `SettingsScreen`'s `ProfileCard` gained a `Share` `IconButton` next to the profile name (title
`Row` now `weight(1f)` + icon, matching `ColorSection`'s title-row-with-trailing-action shape from
`ProfileEditorScreen`). Tapping it calls `shareCard`, storing the returned `Uri` in screen-level
state; a non-null `Uri` shows a new `SharePreviewDialog` (plain `AlertDialog`, decoding the PNG via
`BitmapFactory.decodeStream` off the content `Uri` + `asImageBitmap()`, same decode-and-display shape
`HistoryScreen` already uses for thumbnails) with a Share button that fires
`Intent.createChooser(ACTION_SEND, "image/png")` carrying the same `Uri` with
`FLAG_GRANT_READ_URI_PERMISSION` - no separate "confirm" step beyond the preview itself, since the
preview *is* what the issue calls the required preview step.

No unit test for the renderer per the issue's own spec ("Checked manually on device (no unit tests
for the renderer in v1)") - `./gradlew assembleDebug test` passes with no new failures. Verified by
reading through the two-pass measure/draw logic for both a populated and an empty-list profile
shape, and by the fact `SharePreviewDialog`'s decode path mirrors `HistoryScreen`'s already-working
`BitmapFactory.decodeFile`/`asImageBitmap` pattern (same Robolectric/JDK-26 gap noted since #3 for
anything requiring an actual Compose render pass).

## 2026-09-23 - Issue #14: Palette import from an image (screenshot)

New `ui/paletteimport/` flow, started from a "Import palette from photo" `TextButton` added to
`ProfileEditorScreen` (below the two `ColorSection`s) via a new `Destination.PaletteImport`
route carrying the `profileId`. Same photo -> region -> extract shape as Rate Clothing/Match
Object, but region marking is a *drag* (`detectDragGestures`, not `detectTapGestures`) producing a
`RectRegion` in bitmap-pixel space, run twice in sequence (Best area, then Avoid area, each
skippable via a dedicated Skip button that just advances with an empty swatch list) rather than the
single white-sheet tap those flows use. `ColorExtractor.extract()` already took `correction` as
nullable and `region`/`clusterCount`/`minShare`/`maxColors` as parameters (issue #5's shape), so no
signature change was needed - `PaletteImportViewModel` just calls it with `correction = null` (no
white-balance for a screenshot) and three new `CalibrationConfig` constants
(`PALETTE_IMPORT_QUANTIZER_CLUSTER_COUNT = 24`, `PALETTE_IMPORT_MIN_COLOR_SHARE = 0.01`,
`PALETTE_IMPORT_MAX_COLORS = 24`) sized for "many small swatches in one region" rather than the
existing clothing/object constants sized for "one dominant garment color".

Review screen (`PaletteImportUiState.Reviewing`) holds two independent `List<ImportSwatch>` (Best/
Avoid), each item carrying a locally-unique `id` (a ViewModel-held counter, not a DB id - nothing's
persisted until Confirm) so extracted swatches, manually hex-added swatches, and removals can all
be addressed uniformly. Deselecting a swatch (`Checkbox`, same pattern as `MatchObjectScreen`'s
multi-select) keeps it in the list but excludes it from import, distinct from removing it outright;
"Add to profile" (`confirmImport`) calls the existing `ProfileRepository.addColor` once per
*selected* swatch in each list - no new repository method needed, since `addColor` already appends
at the next position, which is exactly "confirmed colors are appended to the profile's existing
lists" by construction, including across multiple import runs.

`ColorExtractorTest` gained `syntheticSwatchGridReturnsOneColorPerSwatch`, the issue's required
unit test - but getting a *reliable* synthetic grid took a few tries: the underlying Celebi
quantizer (Wu boxes + k-means refinement) doesn't cleanly separate every set of "obviously distinct"
solid colors regardless of `clusterCount` requested. Six pure RGB-cube-corner colors (adding
magenta and either black or white to the four already-separable red/green/blue/yellow) reliably
collapsed two pairs into blended averages, independent of `clusterCount` in {6, 8, 12, 16, 24, 32} -
looks like an early-termination quirk in `QuantizerWu.createBoxes`'s variance-based cut loop rather
than anything share/threshold related. Swapping the sixth swatch from magenta to white produces six
boxes that all separate cleanly at every tested `clusterCount`, so the test's swatch grid is red/
green/blue/yellow/cyan/white (3x2), matching this codebase's actual `PALETTE_IMPORT_*` constants
rather than a round `clusterCount`.

`./gradlew assembleDebug test` passes (1 new `ColorExtractorTest` case). No UI test for the new
drag-to-mark-rectangle interaction or the review screen (same Robolectric/JDK-26 gap noted since
#3) - verified by reading through the state machine and by `MatchObjectScreen`'s existing
`Checkbox`-multi-select and `CalibratingStep`'s tap-to-region conversion math already having passing
render paths to model this screen's `ReviewingStep`/`MarkingAreaStep` on.

## 2026-09-23 - Issue #13: Settings - default color wheel and balance mode

New `data/settings/SettingsRepository` (`DataStoreSettingsRepository`), a thin wrapper over the
`AppContainer.settingsDataStore` that #9 already created but never used - `observeDefaults(): Flow
<HarmonyDefaults>` plus `setDefaultWheel`/`setDefaultBalance`, storing each enum by its `.name` as
a `stringPreferencesKey` (same "store enums as strings, parse defensively" spirit as `HistoryConverters`,
except here a missing/unrecognized value falls back to `PERCEPTUAL`/`FAITHFUL` rather than failing,
since unlike Room there's no migration path for a stale DataStore key). `AppContainer` gained
`settingsRepository`, built from the existing `settingsDataStore` property.

`ui/settings/`: new `SettingsViewModel` (same `StateFlow` + `viewModelScope.launch` factory pattern
as `ProfilesViewModel`/`HistoryDetailViewModel`) exposing `defaults` and the two setters.
`SettingsScreen` gained a "Defaults for new object results" section above Profiles, reusing #12's
`HarmonyOptionsControls` composable directly (it was already `internal`, so no visibility change
needed) - same dropdown/segmented-row UI as the live result screen and History detail, just wired
to the stored default instead of one entry's last-used value. `SettingsScreen`'s single `viewModel`
parameter split into `profilesViewModel`/`settingsViewModel` to host both.

`MatchObjectViewModel.confirmColorSelection()` now reads `settingsRepository.observeDefaults().first()`
right before saving, instead of the hardcoded `PERCEPTUAL`/`FAITHFUL` constants #11/#12 left as a
placeholder for this issue - satisfies "new object results use the defaults" by construction, since
that's the only place a wheel/balance gets chosen for a brand-new entry. Reopened entries are
unaffected: `HistoryDetailViewModel`/`HistoryDetailScreen` already read `entry.wheel`/`entry.balance`
straight off the stored row (#12), never touching Settings.

New `DataStoreSettingsRepositoryTest`: builds a real `PreferenceDataStoreFactory` over a temp file
(pure JVM, no Robolectric needed - `datastore-preferences` doesn't touch `android.*`) - empty-store
fallback, each setter persists without disturbing the other, and both together round-trip through
the same repository instance. (A cross-instance "close and reopen" case was tried and dropped:
DataStore refuses a second concurrent instance over the same file path even after the first's last
write completes, so that shape isn't testable without an explicit close API this artifact doesn't
expose - the same-instance round-trip already covers the encode/decode logic.)

`./gradlew assembleDebug test` passes (4 new `DataStoreSettingsRepositoryTest` cases). No UI test
for the new Settings controls or for `MatchObjectViewModel`'s default read (same Robolectric/JDK-26
gap noted since #3; `MatchObjectViewModel` still has no dedicated test file, same as before this
issue) - verified by reading through the wiring and by `HarmonyOptionsControls` already having a
passing render path from #12.
