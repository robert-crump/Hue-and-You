## 2026-09-25 - Issue #28: In-app CameraX viewfinder with center-box overlay and gallery button

Both photo flows' `PickingPhoto` step now renders a new shared `CameraCaptureStep`
(`ui/common/CameraCaptureStep.kt`) instead of the old two-button "Take photo / Pick photo" screen -
`MatchObjectScreen` and `RateClothingScreen` each just wire its `onPhotoUri` callback straight to
their existing `viewModel.onPhotoPicked(context.contentResolver, uri)`, unchanged from here on (same
decode-and-downscale-off-main-thread pipeline as every other photo entry point). `CameraCaptureStep`
requests the `CAMERA` runtime permission once on first composition; granted shows `CameraViewfinder`
(new CameraX `Preview` + `ImageCapture` bound to `ProcessCameraProvider` via an `AndroidView`-wrapped
`PreviewView`, the back camera, a shutter `FloatingActionButton`, and a corner gallery `IconButton`),
denied falls back to `CameraPermissionFallback` (a "Pick from gallery" button plus, only after an
actual denial rather than merely not-yet-granted, a denial message and an "Open Settings" button so
permission can still be granted later) and auto-launches the gallery picker once so the user isn't
stuck. The shutter captures to a temp file in the same `cacheDir/camera_captures` FileProvider path
the old system-camera intent used (`ImageCapture.OutputFileOptions` + `FileProvider.getUriForFile`),
guarded by an `isCapturing` flag against double-taps; the gallery button and the fallback's button
both reuse one `ActivityResultContracts.PickVisualMedia()` launcher owned by `CameraCaptureStep`.

The overlay box reuses `CalibrationConfig.CENTER_BOX_FRACTION` and the same `drawMarkerRect`
`DrawScope` extension `PhotoResultSection` already draws its center-box marker with (widened from
`private` to `internal` so both files in `ui.common` share it) - the two are guaranteed to match
since they're the same constant and the same drawing code, not just visually similar. The old
`ActivityResultContracts.TakePicture()` system-camera launch (and its per-screen
`createCameraPhotoUri`/`pendingCameraUri`) is deleted from both screens; the `FileProvider`
declaration and its `camera_captures`/`share_cards` cache-paths are untouched since CameraX's own
file output and `ShareCardRenderer` still need them. Added the CameraX (`camera-core`/`camera2`/
`lifecycle`/`view`, 1.4.2) and `lifecycle-runtime-compose` dependencies, plus a manifest
`CAMERA` permission and an optional `android.hardware.camera` `<uses-feature>` (optional since the
gallery fallback means the app still works on a camera-less device). Removed the now-orphaned
`pick_photo_reminder`/`rate_clothing_take_photo` strings (the old screen's copy) and added
`camera_viewfinder_hint`/`camera_shutter_content_description`/`camera_permission_denied_message`/
`camera_open_settings`.

Rotation and the live-preview/capture pipeline itself are standard CameraX behavior (`PreviewView`
and `ImageCapture` both handle sensor/device rotation internally) rather than anything this issue's
code manages by hand, so there's nothing bespoke to unit-test there. Back from the viewfinder was
already correct with no change needed - `PickingPhoto` is a state within the existing screen, not a
separate nav destination, so the screen's existing top-bar back arrow (`onNavigateBack` ->
`navController.popBackStack()`, both routes are one hop from home) already lands on the home screen.

Test: no new automated test - this issue is almost entirely `PreviewView`/`ProcessCameraProvider`/
`ImageCapture` wiring plus runtime-permission branching, none of which is unit-testable without
Robolectric or an instrumented device (same JDK-26/no-`adb` gap noted since #3, and CameraX's own
Compose/`AndroidView` integration has no meaningful pure-function surface to extract here) - verified
by reading through the permission branches (granted/first-request/denied-with-fallback) and the
shutter's file-write-then-`FileProvider`-wrap-then-existing-`onPhotoPicked` call chain. No manual
on-device check was possible in this environment (no attached device/emulator) - flagged per the
issue's own "manual check on device" AC as unverified rather than claimed done.
`./gradlew :colorspace:test :app:testDebugUnitTest assembleDebug lintDebug` all pass.

## 2026-09-25 - Issue #26: Long-press any color circle to copy its hex code

New shared `ColorCircle` composable (`ui/common/ColorCircle.kt`) replaces every ad hoc
`Box.clip(CircleShape).background(Color(argb))` swatch in the app: `PaletteResultBody`'s verdict
circle, `HarmonyResultView`'s `ColorSwatch` (renamed away - callers now use `ColorCircle` directly),
and `PhotoResultSection`'s `ColorChip` (current/alternative chips, which keeps its tap-to-pick
`onClick` and selected-border via new `border: BorderStroke?`/`onClick: (() -> Unit)?` params) all
route through it, as does the Best/Avoid list in `ProfileEditorScreen`. Since `PaletteResultBody`/
`HarmonyResultBody` are shared with History detail (unchanged call sites), its circles pick up the
same behavior there for free. Deliberately *not* touched: the AddColorDialog color-picker preview
circle (hex is an input there, not a display) and the small best-colors preview strip in
`SettingsScreen`/`PaletteImportScreen` - neither is in the issue's enumerated list of circles.

Long-press copies `formatHexColor(argb)` via `LocalClipboard`/`ClipEntry` (not the deprecated
`LocalClipboardManager.setText`, since this compose-bom already has the suspend-based clipboard
API) inside a `rememberCoroutineScope().launch`, plus `LocalHapticFeedback.performHapticFeedback
(HapticFeedbackType.LongPress)` - no app-side toast/snackbar per the AC (minSdk 37 shows the
system's own confirmation). Built on `Modifier.combinedClickable` with `onClick` optional
(non-interactive circles like the verdict card pass none, and get `indication = null` so they don't
gain a spurious ripple) so existing tap behavior (chip selection) is unaffected. The hex `Text` under
circles in `ProfileEditorScreen`'s Best/Avoid list is deleted (replaced by a `Spacer(weight(1f))` to
keep the move/remove icon buttons right-aligned); hex is untouched in the color picker dialog, the
share card and the JSON backup, none of which render a circle from this list.

Test: no new Compose UI test for the clipboard-after-long-press AC - same Robolectric/JDK-26
environment gap noted since #3 (confirmed still true: this JDK is 26.0.1, `adb` isn't available
either, so no path to a real instrumented test in this environment) - verified by reading through
`ColorCircle`'s `combinedClickable` wiring and each call site's parameters instead. No other tests
affected (no new/changed pure functions - `formatHexColor` is unchanged and already covered).
`./gradlew :colorspace:test :app:testDebugUnitTest assembleDebug lintDebug` all pass.

## 2026-09-25 - Issue #25: Remember last-used profile and switch profile on the clothing result

`RateClothingUiState.SelectingProfile` is gone - the profile-selection step never runs anymore.
`RateClothingViewModel.init` reads `SettingsRepository.observeLastUsedClothingProfileId()` (new
`Flow<Long?>` backed by a `longPreferencesKey`, alongside the existing harmony-defaults keys in the
same `hue_and_you_settings` DataStore) and picks `profiles.firstOrNull { it.id == lastUsedId } ?:
profiles.first()` - so a deleted remembered profile silently falls back to the oldest profile
(`ProfileDao` already orders by `createdAt ASC`) with no error state. `ShowingResult` carries the
full `profiles` list plus `selectedProfile` so `RateClothingScreen` can render the new clickable
"For: <name>" line (only when `profiles.size >= 2`) without a second query; tapping it opens a
`ProfilePickerDialog` (an `AlertDialog` wrapping the same clickable-row list the old selection step
used) and picking a profile calls the new `RateClothingViewModel.switchProfile(profile)`.

`switchProfile` re-scores the *current* `argb` against the new profile synchronously (same
"state updates instantly, persistence follows" pattern as `pickCandidate`/`pickAtPoint` from #22),
then in a coroutine calls both `SettingsRepository.setLastUsedClothingProfileId` and a new
`HistoryRepository.updateClothingProfile(entryId, profile, score)` - a straight `UPDATE` of
`profileId`/`profileName`/`bestColorsArgb`/`avoidColorsArgb`/the four score columns on the existing
row (mirrors `updateClothingPick`'s shape, just swapping color+sample for profile+score). Switching
to the already-selected profile is a no-op (checked by id) so it doesn't spuriously overwrite the
remembered id or touch History. No Room schema change - `updateClothingProfile` is a new `HistoryDao`
query over existing columns, and the DataStore key is additive like the harmony-default ones.

Test: new `RateClothingViewModelTest` (the flow had no dedicated ViewModel test before this issue,
noted as a gap since #20/#22) covers remember-when-present, fallback-when-deleted, first-run-with-
nothing-stored, switch (rescore + persisted history update + remembered id) and switch-to-same-
profile-is-a-no-op, using the same reflection-invoked `extractAndSaveResult` + `Unsafe`-allocated
`Bitmap` pattern as `MatchObjectViewModelTest`. `DataStoreSettingsRepositoryTest` gained two cases
for the new key. `DefaultHistoryRepositoryTest` gained `updateClothingProfile_...InPlace`. Every
other `HistoryRepository`/`SettingsRepository` fake in the test suite (`MatchObjectViewModelTest`,
`HistoryViewModelTest`) got the two new interface methods stubbed to throw, since they don't
exercise this path. `./gradlew :colorspace:test :app:testDebugUnitTest assembleDebug` all pass.

## 2026-09-25 - Issue #24: Rate Clothing verdict card - Yes / Avoid / Neither

New pure function `ClothingVerdict.forScore(score: PaletteScore)` (colorspace module) replaces
`ColorMatchBand` entirely: Yes/Avoid require the corresponding nearest color to be within a new
`ClothingVerdict.VERDICT_MAX_DELTA_E = 12.0` ΔE00 *and* strictly closer than the other side (so a
tie, or the other side missing, falls through to the next check); Neither covers both-too-far,
either list empty, and ties. Since it derives from the already-stored `PaletteScore` rather than a
new column, History entries scored before this issue still get a verdict for free.

`PaletteResultBody` (shared by the live Rate Clothing result step and History detail, unchanged
call sites in both `RateClothingScreen` and `HistoryDetailScreen`) now renders a single `Card`:
icon (`ThumbUpAlt`/`ThumbDownAlt`/`HorizontalRule`) + verdict text + a 72dp circle of the measured
color, colored by verdict - Yes gets a new fixed-light/dark-green `LocalSuccessColors` (not part of
the dynamic Material scheme, so it needed its own light/dark pair, set in `HueAndYouTheme` via
`CompositionLocalProvider` next to `MaterialTheme`), Avoid uses `errorContainer`, Neither uses
`surfaceVariant`. All deltas, hex codes, nearest-color rows and the "closer to avoid" warning are
gone; the best-guess disclaimer moved off the result page into a top-bar ⓘ `InfoDialog` on
`RateClothingScreen` (new, matching the `MatchObjectScreen`/`HistoryDetailScreen` pattern from
#23) - `HistoryDetailScreen`'s existing ⓘ action is no longer conditional on `OBJECT` since
Clothing entries need it too now. The rename field is also gone from the live Rate Clothing result
page (`RateClothingUiState.ShowingResult.historyEntryName`/`RateClothingViewModel.renameResult`
deleted) - renaming a clothing entry is still possible from its History detail page, unchanged.

`ColorMatch` dropped its `band: ColorMatchBand` field (now just `argb`/`deltaE`); `PaletteScore`
unchanged otherwise, so no schema/migration. `BackupColorMatchDto.band` stays in the JSON schema
(no longer optional/defaulted, so it's always serialized regardless of `encodeDefaults`) written as
a fixed placeholder and ignored on import - verified by a test asserting the key is still present
in serialized JSON and that an import with an arbitrary legacy value round-trips unchanged. Settings
> About's four-band breakdown is replaced by three static strings explaining Yes/Avoid/Neither
(no dynamic threshold text needed here, unlike the old band section - the number itself isn't shown
anywhere in the UI anymore).

Test: new `ClothingVerdictTest` (colorspace) covers Yes/Avoid/Neither, a tie between Best and
Avoid, the exact `VERDICT_MAX_DELTA_E` boundary vs. just over it, and both lists empty individually.
`PaletteScorerTest` lost its `ColorMatchBand` boundary test (moved/superseded by the above).
`DefaultHistoryRepositoryTest`/`BackupSerializerTest` updated for the two-arg `ColorMatch`
constructor; `BackupSerializerTest` gained the band-compatibility tests above. No new Compose UI
test for the card layout/theme-contrast AC (same Robolectric/JDK-26 gap noted since #3) - verified
by reading through the color role choices (all four - success/error/surfaceVariant containers -
already have Material-guaranteed on-container contrast). `./gradlew :colorspace:test
:app:testDebugUnitTest assembleDebug` all pass.

## 2026-09-25 - Issue #23: Simplified Match Object result - Complementary, Analogous, Tonal with info dialogs and neutral hint

`HarmonyRelationship`/`HarmonyEngine.generate` dropped `SPLIT_COMPLEMENTARY`/`TRIADIC` entirely
(enum cases, generation, tests) - only Complementary, Analogous and Tonal remain. Neutral-color
detection is a separate pure function, `HarmonyEngine.isNeutral(chroma)` against a new
`HarmonyConfig.NEUTRAL_CHROMA_THRESHOLD = 12.0`, rather than folded into `generate()` - keeping it
outside `generate()` meant the existing hue/balance tests (which run over arbitrary sample colors)
didn't need auditing for accidental neutrality, and the threshold itself stays boundary-testable
as a plain `Double -> Boolean` (same shape as the old `ColorMatchBand.forDeltaE`) instead of needing
a gamut-mapped round trip through an actual color.

`HarmonyResultBody` (shared by the live Match Object result and History detail) is now just the
relationship rows: no input-color swatch/hex/label section, no disclaimer text. Each row is a
compact `Row` - label + a small ⓘ `IconButton` (32dp touch target, so it doesn't blow out row
height) on the left, ~64dp circles on the right - and tapping the ⓘ opens a new shared
`InfoDialog` (title + one/two sentences + a single OK button, `ui/common/InfoDialog.kt`) with the
fixed explanation text for that relationship. When `HarmonyEngine.isNeutral(chroma)` is true,
Complementary/Analogous are swapped for one plain hint row; Tonal always renders. The same
`InfoDialog` backs a new ⓘ action in `MatchObjectScreen`'s and `HistoryDetailScreen`'s top bars
showing the best-guess disclaimer that used to sit inline - reusing `rate_clothing_best_guess_disclaimer`
rather than a new string.

Wheel/balance and the rename field are gone from both the live result page and History detail -
`HarmonyOptionsControls` now has exactly one caller left (Settings' own defaults, unchanged); new
results still take Settings' defaults, History still reopens with the wheel/balance it was saved
with, but neither is editable from the result/detail screens anymore. Since nothing could still
call it, `HistoryRepository.updateHarmonyOptions`/`HistoryDao.updateHarmonyOptions` (and the SQL
`UPDATE ... SET wheel, balance` query) were deleted outright rather than left as dead code, along
with `MatchObjectViewModel.renameResult`/`setWheel`/`setBalance` and
`HistoryDetailViewModel.setWheel`/`setBalance` and the now-unused `historyEntryName` state field -
the `wheel`/`balance` columns themselves are untouched (still written at creation, still read for
display), so no migration was needed.

Test: `HarmonyEngineTest` lost its split-complementary/triadic assertions and gained
`isNeutralExcludesTheThresholdItselfButIncludesJustBelowIt` (boundary test at exactly
`NEUTRAL_CHROMA_THRESHOLD`). No new Compose UI test for the row/dialog layout or the "fits without
scrolling" AC (same Robolectric/JDK-26 gap noted since #3) - verified by reading through the
layout and manually reasoning about removed vertical space (no hex/name/wheel-balance/disclaimer
lines). `./gradlew :colorspace:test :app:testDebugUnitTest assembleDebug` all pass.
