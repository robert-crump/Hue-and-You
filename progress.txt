## 2026-09-23 - Issue #12: Color wheels (Traditional, Screen) and Faithful/Softened toggle

`Harmony.kt` (`:colorspace`) gained the two remaining `ColorWheelStrategy` implementations and the
second `BalanceMode`, without touching `HarmonyEngine` itself (exactly the seam #11 set up).
`TraditionalWheel` (Goethe/Itten RYB) and `ScreenWheel` (RGB/HSV) both go through a new private
`PiecewiseHueMap`: HCT hue -> the other wheel's hue via linear interpolation between six anchor
points (red/orange/yellow/green/blue/violet for RYB, red/yellow/green/cyan/blue/magenta for HSV),
rotate by the offset there, then map back. The anchor hues aren't round numbers - they're each
primary/secondary's *actual* HCT hue (e.g. pure yellow #FFFF00 is HCT hue ~111, not 60), computed
once via a throwaway test-and-print and hardcoded as starting guesses, same spirit as
`CalibrationConfig`. This makes "yellow's complement is violet" (Traditional) and "yellow's
complement is blue" (Screen) fall out of the anchor table rather than needing special-casing.
`SoftenedBalance` multiplies chroma by `HarmonyConfig.SOFTENED_CHROMA_FACTOR` (0.7) and pulls tone
30% of the way toward `SOFTENED_TONE_TARGET` (65) - both starting guesses in the new `HarmonyConfig`
object. `HarmonyWheel`/`HarmonyBalance` gained `TRADITIONAL`/`SCREEN` and `SOFTENED` entries; Room's
`HistoryConverters` serializes by enum name, so no migration was needed for the wider domain.

`:app`: new shared `ui/common/HarmonyOptionsControls.kt` (`ExposedDropdownMenuBox` for the wheel,
`SingleChoiceSegmentedButtonRow` for Faithful/Softened) used by both the live Match Colors for an
Object result step and `HistoryDetailScreen`'s OBJECT branch - both already recomputed suggestions
from `(inputColorsArgb, wheel, balance)` via `HarmonyResultBody` (#11), so wiring the controls to
that same state makes "updates immediately" true by construction. `HistoryRepository` gained
`updateHarmonyOptions(entryId, wheel, balance)` (new `HistoryDao.updateHarmonyOptions` UPDATE
query) so a change persists as the entry's last-used wheel/balance; `HistoryDetailViewModel`'s
`entry` is a `Flow` off that same row, so after a write the Room invalidation callback redraws the
screen with the persisted value - no separate optimistic-update state needed there.
`MatchObjectViewModel.setWheel`/`setBalance` do update `_uiState` optimistically (no Room-backed
Flow to fall back on mid-session) in addition to persisting, so the live result step feels instant
too. Wheel/balance are still hardcoded to `PERCEPTUAL`/`FAITHFUL` as the *initial* choice on first
save (issue #13 adds a real default).

New tests in `HarmonyEngineTest`: `offsetsPerRelationshipAreCorrectOnEachWheel` now loops over all
three wheels, computing each expected hue via `wheel.strategy.rotate(...)` directly rather than
assuming HCT-space addition (the previous test's shape, now generalized); dedicated
`traditionalWheelComplementOfYellowIsViolet`/`screenWheelComplementOfYellowIsBlue` per the issue's
acceptance criteria; `softenedBalanceLowersChromaAndStaysInGamut`; `allGeneratedColorsAreInGamut`
now sweeps every wheel/balance combination. `FakeHistoryDao` and `HistoryViewModelTest`'s
`FakeHistoryRepository` both needed the new `updateHarmonyOptions` member to keep compiling.

`./gradlew assembleDebug test` passes (7 `HarmonyEngineTest` cases total, up from 4). No UI test
for the new dropdown/toggle (same Robolectric/JDK-26 gap noted since #3) - verified by reading
through the state wiring and by the fact both screens already had a passing render path for
`HarmonyResultBody` from #11.

## 2026-09-23 - Issue #11: Match colors for an object - HarmonyEngine on the Perceptual wheel

New `Harmony.kt` (`:colorspace`, pure Kotlin): `HarmonyEngine.generate(referenceArgb, wheel:
HarmonyWheel, balance: HarmonyBalance)` returns one `HarmonySuggestion` (a `HarmonyRelationship`
plus its `colors: List<Int>`) per relationship - Complementary (+180 deg), Split-complementary
(+150/+210), Analogous (-30/+30), Triadic (+120/+240), Tonal (tones 30/50/70/90 at the reference's
own hue/chroma, excluding whichever tone is closest to the reference's actual tone). Both "wheel"
and "balance" are small strategy interfaces (`ColorWheelStrategy.rotate(hue, degrees)`,
`BalanceMode.apply(reference, hue)`) with a single implementation each for this slice
(`PerceptualWheel` rotates directly in HCT hue; `FaithfulBalance` copies the reference's tone and
chroma onto the rotated hue) - issue #12 (Traditional/Screen wheels, Softened balance) adds more
implementations without touching `HarmonyEngine` itself. `HarmonyWheel`/`HarmonyBalance` enums wrap
those strategy objects and are what gets persisted/selected, same shape as picking a `TypeConverter`-
friendly enum over storing a polymorphic type. Gamut clamping is inherited for free from the
existing `hctToArgb` (Material Color Utilities' in-gamut solver), not reimplemented here.

`data/history`: extended (not replaced) the existing `HistoryEntryEntity`/`HistoryEntry` - new
`inputColorsArgb: List<Int>` (empty for CLOTHING), `wheel`/`balance: HarmonyWheel?`/`HarmonyBalance?`
(null for CLOTHING), all with defaults so every existing CLOTHING call site and test compiles
unchanged. `calibratedArgb`/`score` stay non-null for OBJECT rows too (first selected color /
all-null `PaletteScore`) rather than becoming nullable everywhere, since they're simply never read
for OBJECT entries (the detail screen branches on `entry.type` before touching them). Two new
`HarmonyConverters`-style nullable `TypeConverter`s in `HistoryConverters` for the enums; existing
`List<Int>` converter reused as-is for `inputColorsArgb`. `HistoryRepository` gained
`saveObjectResult(thumbnailPath, inputColorsArgb, wheel, balance)`, parallel to
`saveClothingResult`. Database version bumped 2 -> 3 (still `fallbackToDestructiveMigration`, no
shipped install base).

`:app` UI: replaced `MatchColorsPlaceholderScreen`/`Destination.MatchColorsPlaceholder` with a real
`ui/matchcolors/` flow (`MatchObjectViewModel`/`MatchObjectUiState`/`MatchObjectScreen`,
`Destination.MatchObject`) - photo -> white-sheet tap (same `WhiteBalanceCalibrator`/
`ColorExtractor` pipeline as Rate Clothing, no profile step) -> a `SelectingColors` step with a
`Checkbox` per extracted color (multi-select, unlike Rate Clothing's single-pick - always shown,
even when one color is clearly dominant, since the issue asks for multi-select explicitly) ->
`confirmColorSelection()` saves to History and shows results. Wheel/balance are hardcoded to
`PERCEPTUAL`/`FAITHFUL` for now (issue #13 adds a Settings default and a per-screen picker on top
of this). Moved `Bitmap.toPixelSource()` out of `ui/rateclothing/` into `ui/common/` since both
flows need it now. New `ui/common/HarmonyResultView.kt` (`HarmonyResultBody`) renders one section
per input color, each recomputing its suggestions live via `HarmonyEngine.generate` from the raw
`(inputColorsArgb, wheel, balance)` rather than any stored/precomputed swatch - shared by the live
result step and `HistoryDetailScreen`'s OBJECT branch, so "reopening recomputes suggestions from
stored input colors" is true by construction (same pattern `PaletteResultBody` already established
for CLOTHING, just recomputing more than `ColorMatchBand`). `HistoryDetailScreen` now switches on
`entry.type` between `PaletteResultBody` (CLOTHING) and `HarmonyResultBody` (OBJECT).

New tests: `HarmonyEngineTest` (`:colorspace`) - hue offset correctness per relationship (2.5 deg
tolerance, since gamut mapping can nudge hue slightly for highly saturated reference colors pushed
out of gamut at the rotated hue), tonal excludes the tone closest to the reference and keeps hue/
chroma, Faithful keeps tone exactly and never raises chroma, and every generated color round-trips
to a valid in-gamut ARGB int. `DefaultHistoryRepositoryTest` gained two `saveObjectResult` cases
(default name/type, and a storage round-trip for input colors + wheel + balance).

`./gradlew assembleDebug test` passes (4 new `HarmonyEngineTest` cases, 2 new
`DefaultHistoryRepositoryTest` cases). No UI/instrumented test for the new screen or the
multi-select checkboxes (same Robolectric/JDK-26 limitation noted since the #3 entry, still no
emulator/device in this environment) - verified by reading through the state machine and Compose
tree instead, mirroring Rate Clothing's own photo-flow screens which have the same gap.

## 2026-09-23 - Issue #10: History - rename and delete with undo

Rename (AC "user can rename an entry from the History list") was already fully implemented as
part of #9 - `HistoryDetailScreen` (reached by tapping a row in the list) has a name text field
wired to `HistoryRepository.renameEntry`, and it persists. This issue's real remaining scope was
delete-with-undo, so that's all that's new here.

Delete uses the "hide immediately, delete for real once the undo window elapses" pattern rather
than an `AlertDialog` confirmation (unlike `ProfileEditorScreen`'s profile delete) - the issue's
ACs ask for confirmation *or* undo, and a Snackbar-with-Undo covers "guarded against accidents"
without an extra modal tap, while giving a real, literal undo (as opposed to a dialog, which can
only prevent the delete, not reverse one already committed). `HistoryViewModel` gained a
`pendingDeletions: MutableStateFlow<Map<Long, HistoryEntry>>` (id -> the full entry, so the
Snackbar can show its name) plus a `pendingDeletionJobs` map of the scheduled finalization
coroutines. `uiState` is now `combine(repository.observeEntries(), pendingDeletions)`, filtering
pending ids out of the visible list - so the entry disappears from the list the instant delete is
tapped, before any real deletion happens. `deleteEntry(entry)` marks it pending and schedules a
`viewModelScope.launch { delay(UNDO_WINDOW_MILLIS); repository.deleteEntry(...) }`; `undoDelete(id)`
just cancels that job and unmarks the id - since nothing was actually touched in the repository
yet, undo is trivially "full" restoration (thumbnail included) with no snapshot/restore logic
needed. The known tradeoff (noted rather than solved, since nothing else in this app persists
transient ViewModel state across process death either - see the #7 entry's `currentBitmap`): if
the process dies during the ~4s undo window, the pending delete is silently abandoned and the
entry survives - never silently lost data, just a surprising "it came back" if it happens.

`HistoryRepository` gained `deleteEntry(entryId)`, implemented in `DefaultHistoryRepository` by
reading the entity first (for its `thumbnailPath`), deleting the Room row, then deleting the
thumbnail file via a new `ThumbnailStore.delete(path)` - satisfies "thumbnail file is removed once
deletion is final" by construction, since this function *is* what "final" means (nothing else
calls it during the undo window). `HistoryDao` gained a one-shot `getEntry` (suspend, not `Flow`)
alongside the existing `observeEntry`, plus a plain `DELETE ... WHERE id = :entryId` query.

UI: `HistoryScreen`'s row gained a trailing delete `IconButton`; the screen now wraps its content
in a local `Scaffold` (nested under the nav host's own bottom-bar `Scaffold`, same as any
per-screen `Scaffold` needing its own `SnackbarHost` in a bottom-nav app) with a `SnackbarHost`,
and a `LaunchedEffect` keyed on the pending entry's id shows the "Deleted "<name>"" / Undo
snackbar and calls `viewModel.undoDelete` on `SnackbarResult.ActionPerformed`.

`./gradlew assembleDebug test` passes, including a new `HistoryViewModelTest` (`StandardTestDispatcher`
+ manual `advanceUntilIdle`/`runCurrent`, since the delete/undo logic is defined by *when* things
happen relative to the undo window, which `UnconfinedTestDispatcher`'s eager execution would paper
over) covering: hide-on-delete without touching the repository, undo before the window elapses
never calls the repository, and after the window elapses the repository's `deleteEntry` fires.
`DefaultHistoryRepositoryTest` gained a `FakeThumbnailStore` and two tests for the delete path.
No UI/instrumented test for the Snackbar itself (same Robolectric/JDK-26 limitation noted since the
#3 entry) - verified by reading through the composable instead.

## 2026-09-23 - Issue #9: History - auto-save clothing results, list and reopen

New `data/history` package (`:app`): `HistoryEntryEntity` (Room, table `history_entries`, no FK to
`profiles` - deliberately, since AC requires a profile's History entries to stay readable after
that profile is deleted) stores the snapshot as plain columns rather than reusing `:colorspace`'s
`PaletteScore`/`ColorMatch` domain types directly, matching the existing "primitives at the module
boundary" pattern (`nearestBestArgb`/`nearestBestDeltaE`/etc, nullable in pairs; `ColorMatchBand` is
recomputed from `deltaE` via `ColorMatchBand.forDeltaE` on read rather than stored, since it's a
pure function of the ΔE already saved - one less thing to keep in sync). `bestColorsArgb`/
`avoidColorsArgb` (the profile's Best/Avoid lists *at save time*) round-trip through a new
`HistoryConverters` as a comma-joined string - plain values, no JSON library needed since these are
just `List<Int>`. `HistoryEntry` (domain) holds a real `score: PaletteScore`, reconstructed by
`HistoryEntryEntity.toDomain()`; `:app` can freely reference `:colorspace` types (only the reverse
direction is restricted), so this doesn't fight the module boundary the way storing them by-value
does above.

`HistoryRepository.saveClothingResult(thumbnailPath: String, calibratedArgb, profile: Profile?,
score: PaletteScore)` takes an already-saved thumbnail *path*, not a `Bitmap` - keeps
`DefaultHistoryRepository` fully unit-testable with `FakeHistoryDao` (same in-memory-map-plus-
`MutableStateFlow` shape as `FakeProfileDao`) with zero Android framework dependency, since this
repo's app-module unit tests can't touch `android.graphics.*` (Robolectric/JDK-26 limitation, noted
since the #3 entry). The actual Bitmap -> downscaled-JPEG-in-`filesDir` work lives in a separate
`ThumbnailStore`/`FileThumbnailStore` (512px long edge, `context.filesDir/history_thumbnails/`,
`Dispatchers.IO`) that `RateClothingViewModel` calls directly before handing the resulting path to
the repository - not verified by a JVM unit test for the same Bitmap-can't-be-constructed reason as
`ThumbnailStore`'s Android-framework siblings elsewhere in the app, verified by reading through it
instead. Default name is "type + date/time" (`defaultHistoryEntryName`, e.g. "Clothing Sep 23, 2026
3:45 PM") via `java.time` (`minSdk 37`, no desugaring needed).

`HueAndYouDatabase` bumped to version 2 (new `HistoryEntryEntity` + `historyDao()`); `AppContainer`'s
`Room.databaseBuilder` now calls `.fallbackToDestructiveMigration(dropAllTables = true)` since there's
no shipped install base yet to write a real migration for.

`:app` wiring: `RateClothingViewModel` gained `historyRepository`/`thumbnailStore` (both from
`AppContainer`, same factory pattern as `profileRepository`) and a `currentBitmap` field (set in
`onPhotoPicked`, independent of the UI state machine) since the color-selection step
(`SelectingColor`) doesn't itself carry the original bitmap. `confirmCalibration()`'s
clearly-dominant path and `selectColor()` now funnel through `showResult(argb)`, which computes the
`PaletteScore` synchronously (unchanged logic, renamed from the old `resultFor` to `scoreFor`) but
saves to History inside a `viewModelScope.launch` (thumbnail encode + Room insert are real I/O) -
`ShowingResult` only appears once the entry is saved and has its id/name, so by the time a result is
on screen it's already persisted; `RateClothingUiState.ShowingResult` gained `historyEntryId`/
`historyEntryName` fields for this. `renameResult(name)` on the ViewModel persists a rename via
`historyRepository.renameEntry`.

UI: extracted the swatch/hex/closer-to-avoid-warning/ΔE-rows/disclaimer block out of
`RateClothingScreen.kt`'s old private `ResultStep` into a new `ui/common/PaletteResultView.kt`
(`internal` visibility - shared module-wide, not truly public) as `PaletteResultBody`, since both
the live Rate Clothing result step and the new History detail screen need to render the exact same
content from a `PaletteScore` snapshot. `ResultStep` now also has an `OutlinedTextField` for the
name (`rememberSaveable` keyed on `entryId`, same "local state + call the ViewModel on each edit"
pattern `ProfileEditorScreen`'s name field already uses, to avoid Flow round-trip cursor jumps).

New `ui/history/`: `HistoryViewModel` now exposes real `observeEntries()` data instead of a stub;
`HistoryScreen` renders a `LazyColumn` of rows (thumbnail decoded off the main thread via
`produceState` + `BitmapFactory.decodeFile`, name, "type · profile name" subtitle, formatted date),
tappable into a new `Destination.HistoryDetail` route / `HistoryDetailScreen` +
`HistoryDetailViewModel`, which observes one entry by id and reuses `PaletteResultBody` plus the
same editable-name field - "reopening" is just rendering the saved snapshot's `calibratedArgb`/
`score`, so it's naturally unaffected by later profile edits or deletion (nothing re-reads
`ProfileRepository`).

New tests: `FakeHistoryDao` + `DefaultHistoryRepositoryTest` (default name format, profile/score
snapshot fields with and without a profile, newest-first ordering, rename persists, and an explicit
test that mutating a `Profile` object after saving doesn't touch the already-stored snapshot).

`./gradlew assembleDebug test` passes (6 new `DefaultHistoryRepositoryTest` cases). No UI/
instrumented test for the History list/detail screens or thumbnail file I/O (same Robolectric/
JDK-26 limitation noted since the #3 entry) - verified by reading through the Compose tree and
repository wiring instead. Verified no new manifest permissions were introduced (no manifest
changes in this issue).
