## 2026-09-23 - Issue #6: Calibration failures - clipped, too dark, not white

Added real failure *detection* to `WhiteBalanceCalibrator.calibrate` in `:colorspace` (issue #5
only guarded the zero-sampled-pixels edge case; this issue is the "that patch wasn't actually
white/gray" detection deferred there). Three new `WhiteBalanceFailureReason` values, checked in
this order after the existing `NO_SAMPLED_PIXELS` guard:
- `CLIPPED`: while summing the sample circle's pixels, also counts pixels with any raw channel
  (0-255 scale, not linear) at/above `CalibrationConfig.CLIPPED_CHANNEL_THRESHOLD` (250). Fails
  once that count's share of the sample exceeds `CLIPPED_PIXEL_FRACTION_THRESHOLD` (0.05) - both
  are the issue's own starting-guess numbers.
- `TOO_DARK`: converts the sample's averaged linear RGB to Lab and fails if `L` is below
  `MIN_WHITE_LUMINANCE_L` (50.0, a starting guess - a lit white sheet should read far brighter
  than mid-gray).
- `NOT_WHITE`: fails if that same Lab point's chroma (`sqrt(a^2+b^2)`) exceeds
  `MAX_WHITE_CHROMA` (15.0, a starting guess) - reuses `linearRgbToLab` from issue #2, no new
  color math needed.
All four thresholds are `CalibrationConfig` consts, each also a `calibrate(...)` default
parameter (same pattern as the existing `sampleRadiusFraction`), so tests can override
individually. Picked the threshold values against the actual Lab math (via a throwaway Python
port of the sRGB->Lab constants, checked against `ColorConversions.kt` line for line) rather
than guessing blind, so the existing "warm-tinted white" happy-path test and the three new
failure tests all land with real margin, not by luck.

Had to retune the existing `warmTintedWhitePatchIsCorrectedToNeutral` test fixture: its old
color (`0xFFFFE0C0`, R=255) was itself clipped and had chroma ~20 - both of which now correctly
fail before this issue, since nothing previously checked for either. Swapped it for a milder
warm off-white (`0xFFF5E6D3`, L~92, chroma~11) that's still clearly warm-tinted but comfortably
inside both new thresholds - this is a fixture fix caused by adding real detection, not a
weakening of the test.

UI (`:app`, `ui/rateclothing/`): `CalibratingStep`'s failure `Text` now switches on
`WhiteBalanceFailureReason` to one of four distinct string resources (clipped/too-dark/not-white
messages, plus the existing generic one for `NO_SAMPLED_PIXELS`) instead of one generic message
for every failure. Added a second button, "Choose a different photo"
(`RateClothingViewModel.chooseNewPhoto()` resets to `PickingPhoto`), next to the existing
Continue button - re-tapping already worked for free (the photo stays on screen and `onTap` just
overwrites `calibration`), so this covers the acceptance criterion's other half ("re-tap or
choose a new photo") without new state-machine states.

`./gradlew assembleDebug test` passes (3 new calibrator failure tests, 1 existing test fixture
retuned). Verified no new manifest permissions were introduced.

## 2026-09-23 - Issue #5: Calibrate and extract - white-sheet tap and dominant colors (happy path)

Built the deep logic in `:colorspace` (pure Kotlin, so it's fully unit-testable without a
device/emulator) plus the UI wiring in `:app` that replaces the old Rate Clothing placeholder.

`:colorspace` additions:
- `PixelSource` (interface: `width`/`height`/`pixelAt`) decouples the calibration/extraction
  math from `android.graphics.Bitmap` - `:colorspace` is a pure-JVM module and can't reference
  Android framework classes. `IntArrayPixelSource` is the flat-array implementation, used
  directly by tests and (via `:app`'s new `Bitmap.toPixelSource()` extension, which bulk-copies
  via `getPixels` rather than a slow pixel-by-pixel `getPixel` loop) by the real screen.
- `WhiteBalanceCalibrator.calibrate(pixels, tapX, tapY)` samples a circular patch (radius =
  `CalibrationConfig.WHITE_SAMPLE_RADIUS_FRACTION` of the image's short edge) in linear RGB,
  averages each channel, and returns a `WhiteBalanceCorrection` (per-channel scale factors) that
  maps that average to neutral gray - a diagonal, von-Kries-style correction, not a full CAT
  matrix, since the issue only asked for RGB channel scaling. Returns a sealed
  `WhiteBalanceResult` (`Success`/`Failure`); the only failure case wired up is "tap landed where
  the sample circle has zero in-bounds pixels" - real failure *detection* (e.g. "that patch
  wasn't actually white/gray") is explicitly a separate issue, so `Failure` only guards the
  divide-by-zero/out-of-bounds edge case for now.
- `ColorExtractor.extract(pixels, correction?, region?, exclusion?)` crops (optional
  `RectRegion`), skips an optional `CircleRegion` (the white-sample patch), applies the
  correction, and quantizes via `QuantizerCelebi` (Wu boxes + weighted k-means) from the
  `material-color-utilities` dependency already in the version catalog - this is the same
  quantizer Material You uses for wallpaper theming, and matches the issue's "MCU (Celebi)"
  wording exactly, so no new dependency was needed. Colors below `MIN_COLOR_SHARE` are dropped
  and the list is capped at `MAX_COLORS`; "clearly dominant" (`DOMINANT_MIN_SHARE` and
  `DOMINANT_MIN_RATIO_TO_RUNNER_UP`) is computed from the *unfiltered* sorted list so a
  runner-up that gets dropped by the share filter can't accidentally make a borderline top
  color look more dominant than it is.
- All six thresholds live in one `CalibrationConfig` object (const vals), each also exposed as
  a default parameter on `calibrate`/`extract` so tests can override individual values without
  touching global state.
- New tests: `WhiteBalanceCalibratorTest` (warm-tinted synthetic white patch corrects to
  R=G=B; tap fully outside the image fails cleanly) and `ColorExtractorTest` (two solid regions
  return both colors at ~50/50 share; a solid image is flagged clearly-dominant at 100% share;
  an excluded circular region's color never appears in the result, verified by filling that
  region with a color - white - that would otherwise clear the share threshold).

`:app` (`ui/rateclothing/`, replacing `RateClothingPlaceholderScreen.kt`): `RateClothingScreen`
is a state machine (`RateClothingUiState`: `PickingPhoto` -> `LoadingPhoto` -> `Calibrating` ->
`SelectingColor` or straight to `ShowingResult` if clearly dominant). Photo selection uses the
system Photo Picker (`ActivityResultContracts.PickVisualMedia`, no runtime permission needed).
The picked photo is decoded via `ImageDecoder` with `ALLOCATOR_SOFTWARE` (hardware bitmaps can't
do pixel readback) and downscaled to a max 1024px side (`MAX_PHOTO_DIMENSION_PX`) so calibration/
extraction stay fast on full-resolution camera photos - this is a practical decode-time concern,
not one of the domain thresholds, so it's a local constant in the ViewModel rather than added to
`CalibrationConfig`. The image is displayed at its exact aspect ratio (`Modifier.aspectRatio`)
so tap coordinates scale linearly to bitmap pixels with no letterboxing math. Re-tapping just
re-runs calibration and overwrites the previous result; the "Continue" button is only enabled
once `calibration` is a `Success`, which is what enforces "extraction cannot run before a
successful calibration" - confirmCalibration() also independently guards on the same cast, so a
future caller of the ViewModel can't bypass it either. The clothing-result screen (matching
against a saved profile) is out of scope here per the issue - `ShowingResult` just shows the
calibrated swatch and its hex.

`./gradlew assembleDebug test` passes. No UI/instrumented test for the tap gesture or Photo
Picker flow itself (same Robolectric/JDK-26 limitation noted in the #3 entry, and still no
emulator/device available in this environment) - verified by reading through the gesture math
and state transitions instead. Verified no new manifest permissions were introduced.

## 2026-09-23 - Issue #4: Profile editor color picker and reordering

Extended the Profile editor (`ProfileEditorScreen.kt`) from hex-only entry to also
support a visual picker, and added reordering within each color list:

- `AddColorDialog` now has a `SingleChoiceSegmentedButtonRow` ("Hex" / "Picker") toggle.
  Picker mode drives three Material3 `Slider`s (hue 0-360, saturation 0-1, brightness
  0-1) through `android.graphics.Color.HSVToColor` (no new dependency - this is plain
  Android SDK, fine to use from `:app` since it's not the pure-JVM `:colorspace`
  module) and shows a live swatch + the resulting hex via `colorspace.formatHexColor`.
  Rather than plumbing a new argb-accepting path through the ViewModel/repository, the
  picker just computes a guaranteed-valid hex string and reuses the existing
  `addColor(kind, hex, invalidHexMessage)` call - kept the surface area of this change
  to the dialog only.
- Reordering is up/down icon buttons per row (not drag-and-drop - no reorder library
  is in the version catalog, and up/down buttons are simpler to get right and to test
  than implementing drag gestures from scratch for one issue). Buttons disable at each
  list's boundary.
- New `MoveDirection` enum (`UP`/`DOWN`) alongside `ColorKind`.
  `ProfileDao` gained `getColor`, `getColorsForKind` (ordered by `position`), and
  `updateColor`. `RoomProfileRepository.moveColor` reads the color's siblings within
  its own `profileId + kind`, swaps `position` with the adjacent sibling, and no-ops at
  either boundary. `ColorKind` isolation falls out for free since siblings are always
  queried by `(profileId, kind)`. Order was already persisted via `position` and
  already flows into `Profile.bestColors`/`avoidColors` (sorted in `toDomain()`), and
  the Settings profile-card swatches already render that list in order - so no changes
  were needed there for the "reflected on profile card" acceptance criterion, it was
  already wired correctly by issue #3.
- `FakeProfileDao` (test double) and `FakeProfileRepository` (in
  `ProfileEditorViewModelTest`) both had to grow matching methods, since Kotlin
  interfaces don't allow partial implementation - a reminder for future DAO/repository
  interface changes that both test doubles need updating.

`./gradlew assembleDebug test` passes (10 repository tests incl. 4 new move-boundary/
kind-isolation cases, 4 ViewModel tests incl. 1 new delegation case). Verified no new
permissions in the merged manifest. No UI/instrumented test for the picker sliders or
button taps themselves (same Robolectric/JDK-26 limitation noted in the #3 entry, and
still no emulator/device available in this environment).

## 2026-09-23 - Issue #3: Profiles (create, rename, delete, add/remove colors by hex)

Wired up Room for the first time (deferred from issue #1/#2). Used **KSP**, not kapt:
tested `com.google.devtools.ksp` against this repo's Kotlin 2.4.20 even though the KSP
plugin portal's newest published pairing is `2.3.12` (KSP has apparently decoupled its own
versioning from a strict per-Kotlin-version pairing as of its 2.3.x line) - `:app:kspDebugKotlin`
and a full `assembleDebug test` both succeeded, so this is confirmed working, not just
theorized. Added `libs.plugins.ksp` (root `build.gradle.kts` applies it `apply false`,
`:app` applies it for real) and `ksp(libs.androidx.room.compiler)`.

Data layer lives under `com.example.hueandyou.data.profile` in `:app` (needs a live
Android `Context` for `Room.databaseBuilder`, so it couldn't go in the pure-JVM
`:colorspace` module):
- `ProfileEntity` / `PaletteColorEntity` (`Room`, FK cascade-delete from profile to its
  colors) + `Converters` (ColorKind <-> String) + `ProfileWithColors` (`@Relation`).
- `ProfileDao`: flows for the profile list and a single profile-with-colors, plus
  suspend CRUD; `nextPosition(profileId, kind)` computes the next append position so Best
  and Avoid colors keep independent, stable orderings.
- `ProfileRepository` (interface) / `RoomProfileRepository` (impl): the only place that
  knows about Room - it maps `ProfileWithColors` to the plain `Profile`/`PaletteColor`
  domain types the UI sees, splitting/sorting colors by kind+position. Timestamps come
  from an injectable `currentTimeMillis: () -> Long` (defaults to `System::currentTimeMillis`)
  specifically so tests can control `createdAt`/`updatedAt` deterministically.
- `AppContainer`/`DefaultAppContainer` now also builds the (lazy, singleton) `RoomDatabase`
  and exposes `profileRepository`.

UI: `SettingsScreen` now renders a "Profiles" `LazyColumn` section (header + add button +
per-profile cards with name and Best-color swatches) instead of the old placeholder text;
`ProfileEditorScreen` (new) has the name field, two color sections (Best / Avoid) each with
an add-by-hex dialog (validated via `colorspace.parseHexColor`, inline error on bad input)
and a per-color remove button, plus a delete-profile flow gated by an `AlertDialog`
confirmation. Both screens get their ViewModel via a small `viewModelFactory { initializer
{ ... } }` companion function that reaches into `HueAndYouApplication.container` - this
project still has no DI framework, so this is the established manual-DI pattern going
forward for any screen needing repository access (`SettingsViewModel` placeholder class
was deleted, replaced by `ProfilesViewModel`).

Navigation: `Destination.Settings` route gained an optional `scrollToProfiles` bool query
arg (`Destination.Settings.route(scrollToProfiles = true)`) so other screens can deep-link
into Settings pre-scrolled to the Profiles section (this is what issue #8's "no profile"
dialog on Rate Clothing will need - not built here, just the addressable route + the
`LaunchedEffect` that calls `listState.animateScrollToItem(0)` when the flag is set).
Added `Destination.ProfileEditor` (`profile_editor/{profileId}`, `NavType.LongType`).
Important: `TopLevelDestination` needed a separate `navRoute` field from `destination.route`
- the latter is the *template* string (with `{scrollToProfiles}` literally in it) used to
register the composable, and is not itself a navigable route once a destination takes args.

Testing gotcha worth recording: tried Robolectric (`4.17`) for a real in-memory-SQLite Room
DAO test first, since that would exercise the actual `@ForeignKey`/`@Relation` annotations
end to end. It failed hard on this machine's JDK (Gradle's launcher/toolchain JVM is 26.0.1)
with `IllegalAccessException: module java.base does not export jdk.internal.access` inside
Robolectric's `FileDescriptorInterceptor` - a JDK-internals shim Robolectric 4.17 doesn't yet
support on JDK 26. Rather than fight `--add-opens` flags for an unsupported JDK/Robolectric
combination, switched to a hand-written `FakeProfileDao` (in-memory, implements the real
`ProfileDao` interface) and tests `RoomProfileRepository` against that - this covers the
repository's own logic (timestamping, position assignment, kind-splitting, mapping to domain
types) but does NOT verify Room's own cascade-delete/relation-query behavior against real
SQLite. If a future issue needs that guarantee, it'll need either an instrumented test
(`connectedAndroidTest`, needs a device/emulator - none available in this environment) or a
retry of Robolectric once it/the JDK situation here changes.

`./gradlew assembleDebug test` passes (7 new tests: 5 repository, 2 ViewModel hex/delete
logic). Verified no new permissions in the merged manifest.

## 2026-09-23 - Issue #2: ColorSpace module (conversions, CIEDE2000, hex parsing)

Added a new `:colorspace` Gradle module: pure-Kotlin JVM (org.jetbrains.kotlin.jvm plugin,
no AGP, no Android dependency), so this module is a plain JAR consumable outside the app
too. Public API lives in package com.example.hueandyou.colorspace:
- LinearRgb / Lab / Hct: immutable data classes (Lab and linear RGB on the CIE 0-100 scale,
  not 0-1, so they line up with Y = relative luminance and with the white point).
- argbToLinearRgb/linearRgbToArgb, linearRgbToLab/labToLinearRgb, argbToLab/labToArgb,
  argbToHct/hctToArgb: sRGB math (companding, D65 sRGB<->XYZ matrices, CIE 1976 Lab
  piecewise f/f-inverse) is implemented directly in this module; HCT is NOT reimplemented -
  it delegates to Material Color Utilities' Hct.fromInt/Hct.from/toInt (moved the
  `material-color-utilities` dependency from :app to :colorspace, :app now depends on
  :colorspace via `implementation(project(":colorspace"))` and no longer touches MCU
  directly).
- ciede2000(Lab, Lab): Double - full Sharma/Wu/Dalal (2005) ΔE00 formula.
- parseHexColor(String): Int? / formatHexColor(Int): String - `#RRGGBB`/`RRGGBB`,
  case-insensitive in, `#RRGGBB` uppercase out; alpha is ignored on format and forced to
  0xFF on parse.

Verified CIEDE2000 against the actual published 34-pair Sharma/Wu/Dalal reference table
(fetched from the paper author's site, not reconstructed from memory) - all 34 pairs match
to the table's own 4-decimal precision. Round-trip tests (srgb->linear->srgb,
srgb->lab->srgb, srgb->hct->srgb) run over a fixed set of primaries/secondaries/grays/
arbitrary colors rather than randomized input, to keep the suite deterministic.

Added the `kotlin-jvm` plugin alias to libs.versions.toml/root build.gradle.kts (`apply
false` at root, applied for real in colorspace/build.gradle.kts) - this is unrelated to
and not blocked by the AGP-built-in-Kotlin gotcha below, since that gotcha only affects
Android (AGP) modules; a non-Android module still needs the ordinary Kotlin JVM plugin.

`./gradlew assembleDebug test` (root) and `./gradlew :colorspace:test` both pass.
